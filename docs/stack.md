## 2. 따라나온 결정과 근거

### 2.1 마이그레이션 — Flyway

Spring Boot에 기본 통합돼 있고 **순수 SQL 파일에 순차 버전**입니다. Liquibase의 XML
추상화는 우리 규모에서 얻는 게 없습니다.

부분 유니크 인덱스 3건([TODO.md](../TODO.md) 4단계)처럼 **DB 고유 기능을 그대로 쓸
일이 있어서** SQL을 직접 쓰는 쪽이 맞습니다.

초기 데이터도 마이그레이션에 넣습니다 — `ADMIN` 역할, 초기 관리자 계정, 기본창고
한 행, 메뉴 트리 초기값.

### 2.2 인증 — 세션 쿠키. JWT가 아닙니다

**설계가 정해줬습니다.** 1번에서 퇴사 처리를 `active = false`로 정했습니다
([1-user.md](domain/1-user.md) 2.1).

```
JWT   토큰이 만료될 때까지 유효. 계정을 막아도 즉시 안 끊긴다
세션  다음 요청에서 바로 막힌다
```

**퇴사자 계정이 즉시 막혀야 하는 요구가 있으면 JWT는 답이 아닙니다.** 게다가 브라우저
전용 사내 도구라 JWT가 벌어주는 것(모바일 앱 · 크로스 도메인)이 없습니다.

세션 저장소는 **DB(Spring Session JDBC)**. 서버가 한 대라 인메모리로도 되지만,
재배포할 때마다 전원 로그아웃되는 걸 피합니다.

비밀번호는 BCrypt.

### 2.3 인가 — 커스텀 애노테이션

우리 권한 모델은 `(역할, 메뉴, 행위)`입니다
([1-user.md](domain/1-user.md) 2.5). Spring Security의 롤 기반 표현
(`hasRole('ADMIN')`)과 모양이 다릅니다.

```java
@RequirePermission(menu = "ORDER", action = UPDATE)
```

로그인할 때 유효 권한 집합(`Set<메뉴코드:행위>`)을 세션에 적재하고 이 애노테이션이
검사합니다. `ADMIN` 역할은 검사를 건너뜁니다.

**서버가 매 요청마다 다시 검사합니다.** 화면에서 버튼을 숨기는 건 UX이지 보안이
아닙니다 ([1-user.md](domain/1-user.md) 3장).

사이드바는 별도 API가 **볼 수 있는 메뉴 트리**를 내려줍니다. 메뉴가 DB 마스터라
가능한 방식입니다.

### 2.4 API — REST + OpenAPI에서 타입 생성

```
백엔드   springdoc-openapi 가 OpenAPI 스키마를 자동 생성
프런트   openapi-typescript 로 TS 타입을 생성. 빌드 단계에 포함
```

**언어가 갈렸으므로 타입을 손으로 맞추면 반드시 어긋납니다.** 스키마를 진실로 두고
프런트 타입은 파생물로 만듭니다.

GraphQL을 쓰지 않는 이유는 화면이 필요로 하는 조회가 정해져 있고
([sizing.md](sizing.md) 4.1) 클라이언트가 하나뿐이기 때문입니다.

### 2.5 엑셀 — Apache POI

파싱을 **서버에서** 하기로 했으므로([sizing.md](sizing.md) 4.3) 프런트용 SheetJS가
아니라 POI입니다. 초안의 SheetJS 배포 채널 우려(사내 프록시에서 `cdn.sheetjs.com`
접근)도 같이 사라집니다.

읽기·쓰기 모두 최대 1,500행이라 일반 API로 충분합니다. 스트리밍(SXSSF · 이벤트 API)은
필요해지면 그때 씁니다.

### 2.6 배치 — `@Scheduled`. Spring Batch가 아닙니다

돌릴 게 셋뿐입니다.

```
거래처 담당자 개인정보 파기    3번 · 하루 1회
주문 수령인 개인정보 파기      6번 · 하루 1회
안전재고 미달 집계             8번 · 하루 1회
접속기록 만료분 삭제           operations.md 5.3 · 하루 1회
```

**Spring Batch의 청크·재시작·잡 저장소는 이 규모에서 전부 부담입니다.** 서버가 한
대라 ShedLock 같은 분산 잠금도 필요 없습니다.

파기 작업은 **처리 건수와 실행 시각을 로그로 남깁니다.** 지운 값은 안 남깁니다
([3-partner.md](domain/3-partner.md) 3.2).

### 2.7 테스트 — Testcontainers가 필수입니다

우리 로직의 핵심이 전부 **DB 트랜잭션 안에 있습니다.**

```
입고·출고·실사 확정   테이블 4~5개를 한 번에
재import              컬럼 소유권 · 취소 감지 · 이력 화이트리스트
낙관적 잠금            version 충돌
부분 유니크 인덱스     Postgres 고유 동작
```

**인메모리 DB(H2)로는 검증되지 않습니다.** Testcontainers로 진짜 Postgres를 띄웁니다.

프런트는 vitest. 현재 테스트 0건이고, 최소한 **취소 감지 규칙과 재import 컬럼
소유권에는 회귀 테스트가 있어야 합니다** — 여기가 틀리면 조용히 틀립니다.

### 2.8 알림 — 디스코드 Webhook

팀이 이미 디스코드를 씁니다. 시스템이 상태를 갖게 되어도 **알림은 거기로 가는 게
맞습니다** — 사람을 새 앱으로 이주시키지 않습니다.

```
[수집] {판매처} 신규 N · 갱신 M · 취소전환 K · 오류 E건
[주의] 취소된 주문 N건 감지. 출고 전 확인 필요
[재고] 안전재고 미달 N건
```

Webhook URL은 **서버 환경변수에만** 둡니다. 초안이 "클라이언트에서 직접 호출하면
번들에 박힌다"고 경고했던 문제는 백엔드가 생기면서 자연히 없어집니다.

### 2.9 로컬 환경 — docker compose는 Postgres만

앱은 IDE에서 띄웁니다. DB만 컨테이너로 받으면 **환경 차이가 나는 유일한 곳**이
덮입니다.

```yaml
postgres:16   포트 5432   볼륨 하나
```

### 2.10 빌드 — Gradle

QueryDSL의 애노테이션 프로세서 설정이 Gradle 쪽 사례가 훨씬 많습니다. 팀이 Maven을
쓰고 있으면 바꿔도 됩니다 — 이건 취향입니다.

## 3. 배포 구조

서버 두 대. `dev` 브랜치가 개발, `main`이 운영입니다
([convention/git.md](convention/git.md) 1장).

```
[서버 1대]
  nginx        TLS 종료 · 정적 파일(프런트 빌드) · /api 리버스 프록시
  spring-boot  애플리케이션
  postgres     DB (볼륨)
```

프런트를 Spring Boot의 static으로 넣지 않고 nginx가 서빙합니다. SPA 라우팅 fallback과
TLS를 한곳에서 처리하는 게 단순하고, 프런트만 다시 배포하는 것도 가능해집니다.

### 3.1 사내 서버라서 팀이 책임지는 것

관리형 DB를 안 쓰기로 했으므로 **아래는 자동으로 되지 않습니다.** 수령인 정보와
거래처 담당자 연락처가 이 DB에 있습니다.

| | |
|---|---|
| 백업 | 주기 · 보관 위치 · 암호화 |
| **복구 리허설** | 백업이 실제로 복구되는지 확인. 안 해보면 백업이 아닙니다 |
| 접근 통제 | DB 계정 · 서버 SSH · 방화벽 |
| 보안 패치 | OS · Postgres · JVM |
| 로그 보관 | 접근 로그. 개인정보 조회 이력 |

> **정해졌습니다.** 규칙 전체는 [operations.md](operations.md).
> 백업은 사내 NAS에 하루 1회, 복구 리허설은 분기 1회, 개인정보 접속기록은
> `access_log` 테이블에 화면·API 단위로 남깁니다.

[sizing.md](sizing.md) 4.1에서 계산한 결과입니다.

| | 왜 |
|---|---|
| Redis · 캐시 계층 | 동시 3명. 캐시가 해결할 경합이 없음 |
| 검색 엔진 | 주문 91만 · SKU 3,000. 인덱스로 충분 |

마지막 줄은 프런트에 **이미 만들어져 있습니다** — `useActiveTabInterval`.

## 6. Supabase를 안 쓴 이유

2026-09-02 초안이 Supabase를 확정으로 잡았고,
[domain/scope.md](domain/scope.md) 5장에서 "3단계의 출발점"으로 판정했습니다. **출발점으로 쓰되 채택하지는 않았습니다.**

**범위가 달라졌습니다.** 초안의 v1은 주문 취합 하나였습니다. 지금은 도메인 9개고 그
사이에 트랜잭션 로직이 생겼습니다.

```
입고 확정   원장 + 현재고 + 발주라인 + 발주상태
출고 확정   원장(세트 전개) + 현재고 + 주문상태
재import    컬럼 소유권 + 취소 감지 + 이력 화이트리스트 + 파기 예외
실사 확정   기준 시각 차이 + 원장 + 현재고
```

클라이언트에서 하면 안 되고, Postgres 함수나 Edge Function으로 밀면 **백엔드만큼의
코드를 테스트하기 불편한 환경에서** 쓰게 됩니다.

**그리고 RLS가 벌어줄 게 별로 없습니다.** 우리 권한 모델은 `(역할, 메뉴, 행위)` —
엔드포인트 단위 인가입니다. 팀 전원이 모든 주문을 보므로 행 단위 필터링이 거의
없습니다. Supabase의 가장 큰 장점이 우리 설계와 결이 안 맞습니다.

### 6.1 초안에서 살린 것

| | |
|---|---|
| Postgres | 그대로 |
| 트리거로 이력 남기기 | **애플리케이션으로 옮김.** JPA 엔티티 리스너 + 서비스 계층 |
| 이력 컬럼 화이트리스트 | 그대로 ([6-order.md](domain/6-order.md) 3.3) |
| 디스코드 Webhook | 그대로. 호출 위치만 Edge Function → 서버 |
| 엑셀 파싱 | SheetJS → **Apache POI** (서버로 옮겨서) |
| 검증 라이브러리 | zod는 프런트 전용. 서버는 Bean Validation |
| vitest | 프런트 그대로. 백엔드는 JUnit 5 |
| Realtime 안 씀 | 그대로 |

이력을 DB 트리거가 아니라 애플리케이션에서 남기는 이유는 **`changed_by`와 `source`
때문**입니다. 누가 바꿨는지와 import인지 수동인지는 트리거가 모릅니다. 세션 컨텍스트로
넘길 수는 있지만, 그러면 트리거가 애플리케이션에 의존하게 됩니다.
