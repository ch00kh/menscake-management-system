스택과 무관하게 지금 정할 수 있는 규칙. 레이어 구조 · API 응답 규격 · DB 물리 네이밍처럼
프레임워크와 DB가 정해져야 쓸 수 있는 것은 여기 없습니다 ([TODO.md](../TODO.md) 4단계).

규칙의 목적은 하나입니다. **같은 것을 두 사람이 다르게 부르지 않게 하는 것.**

## 1. 표기 — 한글 업무용어 ↔ 영문 식별자

업무용어의 원본은 **한글**입니다. 화면에 보이는 글자는 한글 그대로 씁니다.
코드 식별자만 영문으로 바꿉니다.

### 1.1 번역이 아니라 지정

"수주"를 누구는 `order`, 누구는 `salesOrder`, 누구는 `receiveOrder`로 적으면 끝입니다.
**용어사전에 1:1로 등록하고, 등록된 값만 씁니다.**

```
수주   salesOrder
발주   purchaseOrder
거래처 partner
전표   voucher
품목   item
```

용어사전은 `docs/domain/glossary.md`에 둡니다 (2단계에서 채웁니다).

**사전에 없는 업무용어는 코드에 쓰기 전에 사전에 먼저 추가합니다.** 이 순서를 어기면
사전이 코드를 못 따라가고, 그때부터 사전은 아무도 안 봅니다.

### 1.2 축약 금지

원칙적으로 줄이지 않습니다. `amount`를 `amt`로, `quantity`를 `qty`로 쓰지 않습니다.
읽는 사람이 매번 해독해야 하고, 줄이는 방식이 사람마다 다릅니다.

**허용 목록** — 여기 있는 것만 예외입니다.

```
id   no   url   api   db   ui   css   html   json   csv
```

`no`는 "번호"입니다 (`voucherNo`). 부정(不)이 아닙니다.

이 규칙을 정하면서 기존 코드도 같이 폈습니다 — `qty` → `quantity`, `amt` → `amount`,
`num()` → `formatNumber()`, `won()` → `formatWon()`.

## 2. 식별자 케이스

| 대상 | 규칙 | 예 |
|---|---|---|
| 파일 · 폴더 | kebab-case | `page-header.tsx`, `tab-store.tsx` |
| 컴포넌트 · 타입 · 인터페이스 | PascalCase | `PageHeader`, `SalesOrder` |
| 함수 · 변수 · 객체 필드 | camelCase | `salesOrderNo`, `findByPartner` |
| 상수 (모듈 최상단 고정값) | SCREAMING_SNAKE_CASE | `MAX_TABS`, `STATUSES` |
| 코드값 (enum 멤버) | SCREAMING_SNAKE_CASE | `IN_PROGRESS` |
| React 훅 | `use` 접두 + camelCase | `useTabStore` |
| 불리언 | `is` · `has` · `can` 접두 | `isActive`, `hasAttachment` |

DB 물리명(테이블·컬럼)은 DB가 정해져야 확정합니다. **논리명은 camelCase로 쓰고**,
물리 변환 규칙(snake_case 등)은 4단계에서 정합니다.

## 3. 공통 값 표기

### 3.1 날짜와 시각

| | 저장 | 표시 |
|---|---|---|
| 날짜 | `DATE` | `2026-09-03` |
| 시각 | `TIMESTAMPTZ` (UTC) | `2026-09-03 14:20` |

**시각은 UTC로 저장하고 화면에서 `Asia/Seoul`로 변환합니다.** 국내 전용 시스템이라도
그렇게 합니다. 클라우드 서버의 기본 타임존이 UTC인 경우가 많아, 저장을 KST로 두면
서버·DB·애플리케이션 중 한 곳만 설정이 어긋나도 9시간짜리 사고가 납니다.

날짜만 다루는 값(전표일자, 납기일)은 시각이 아니라 **`DATE`** 입니다. 타임존을 붙이면
자정 경계에서 날짜가 하루 밀립니다.

형식 문자열은 코드에 흩뿌리지 않고 한 곳에서 관리합니다.

### 3.2 금액과 수량

| | 타입 | 표시 |
|---|---|---|
| 금액 | `DECIMAL(18, 2)` — 원 단위 | `12,637,350` 천단위 콤마 |
| 수량 | `DECIMAL(18, 3)` | 소수부가 0이면 생략 |
| 비율 | `DECIMAL(5, 2)` — 백분율 값 | `52.00%` |

**부동소수(`float` · `double` · JS `number`)로 금액을 다루지 않습니다.** `0.1 + 0.2`가
`0.3`이 아닌 문제가 회계에서는 그대로 사고입니다. 서버는 decimal 타입, 프런트로는
문자열로 넘기고 표시 직전에만 포맷합니다.

수량에 소수를 허용하는 이유는 kg · m · L 같은 단위 때문입니다. 개수만 다루는 품목이라도
타입은 같게 두고 표시에서 정리합니다.

### 3.3 코드값 (enum)

**저장은 영문 SCREAMING_SNAKE, 표시는 한글 매핑.**

```
저장   PENDING | IN_PROGRESS | DONE | ON_HOLD | REJECTED
표시   대기    | 진행         | 완료  | 보류     | 반려
```

DB에 한글을 넣지 않는 이유는 셋입니다. 인코딩 사고, 정렬이 가나다순으로 묶여 업무 순서와
어긋남, 그리고 **표시명이 바뀔 때 데이터를 건드려야 함**. "진행"을 "처리중"으로 바꾸는 건
화면 문구 변경이지 데이터 마이그레이션이 아니어야 합니다.

매핑표는 코드 한 곳에 두고 화면은 거기서 읽습니다.

> `src/data/mock.ts`의 `Status`가 한글 값입니다. 목업이라 예외입니다.

## 4. 식별자 설계

### 4.1 PK — 자동증가 정수

```
id   BIGINT   자동증가
```

ERP는 조인이 많아 인덱스 크기와 정렬 지역성이 성능에 직접 옵니다. UUID는 16바이트에
랜덤이라 인덱스가 흩어집니다. 분산 쓰기나 오프라인 생성이 필요해지면 그때 재검토합니다.

### 4.2 업무번호는 PK와 분리

사용자가 보고 부르는 번호(`SO-2026-0841`, `DOC-2026-1019`)는 **PK가 아닙니다.**
별도 컬럼으로 채번합니다.

```
id            BIGINT    내부 조인용. 화면에 노출하지 않는다
salesOrderNo  VARCHAR   업무번호. 사람이 부르는 이름
```

섞으면 채번 규칙이 바뀔 때(연도 리셋, 자릿수 변경) PK를 건드려야 하고, 그건 모든 FK를
건드리는 일입니다.

### 4.3 공통 감사 컬럼

모든 업무 테이블에 넣습니다. 이름을 통일해야 조회·감사 로직을 한 번만 만듭니다.

```
createdAt   TIMESTAMPTZ   생성 시각
createdBy   BIGINT        생성자 (users.id)
updatedAt   TIMESTAMPTZ   수정 시각
updatedBy   BIGINT        수정자
deletedAt   TIMESTAMPTZ   삭제 시각. NULL 이면 살아 있음
```

**삭제는 논리 삭제(soft delete)를 기본으로 합니다.** ERP에서 전표를 물리 삭제하면
감사 추적이 끊깁니다. 조회는 `deletedAt IS NULL`이 기본 조건입니다.

**예외는 개인정보입니다.** 거래처 담당자 연락처처럼 보관 기간이 정해진 데이터는 기간이
지나면 실제로 지워야 합니다. 논리 삭제만 하면 데이터가 그대로 남아 의무 위반입니다.
어느 테이블이 여기 해당하는지는 도메인이 정해지는 **2단계에서 하나씩 지정**합니다.

기준정보처럼 이력이 필요 없는 테이블은 `deletedAt` 대신 `active BOOLEAN`으로 갈 수도
있습니다. 이것도 2단계에서 테이블별로 정합니다.

## 4.4 레이아웃 번호는 불변

`frontend/src/layouts/registry.ts`의 `no`(1~30)는 **사람과 에이전트 사이의 지시 어휘**입니다.

```
"상품 관리 만들어줘. 레이아웃 1번으로."
```

그래서 PK와 같은 취급을 합니다.

- **재사용 금지 · 재배치 금지.** 오늘 1번이 내일 2번이 되면 과거 지시가 전부 틀어집니다
- 레이아웃을 빼도 **번호는 결번으로 남깁니다**
- 새 레이아웃은 마지막 번호 다음부터 붙입니다
- 이름은 바꿔도 되지만, 번호가 가리키는 **화면 구조**는 바꾸지 않습니다

배경은 [docs/domain/scope.md](domain/scope.md) 2장.

## 6. git

### 6.1 브랜치 — 환경에 대응시킨다

**브랜치가 곧 배포 대상입니다.** 어디에 병합했는지가 어느 서버에 올라가는지를 결정합니다.

```
main   운영 서버      ← dev 에서 릴리스할 때만 병합
 ↑
dev    개발 서버      ← 기능 브랜치가 모이는 곳
 ↑
feature/tab-workspace     작업 브랜치. 병합 후 삭제
fix/command-dialog
```

| 브랜치 | 대응 | 누가 여기에 병합하나 |
|---|---|---|
| `main` | 운영 서버 | `dev` (릴리스), `hotfix/*` |
| `dev` | 개발 서버 | `feature/*`, `fix/*` |
| `feature/*` · `fix/*` | 없음 | 개인 작업 |

접두어는 커밋 타입과 같은 것을 씁니다 — `feature` · `fix` · `refactor` · `docs` · `chore`.
(커밋 타입은 `feat`이지만 브랜치는 `feature`로 풀어 씁니다. 브랜치명은 목록에서 눈으로
읽는 대상이라 줄이는 이득이 없습니다.)

**작업 브랜치는 `dev`에서 따고 `dev`로 돌아갑니다.** `main`에서 따면 `dev`에만 있는
변경을 못 받습니다.

**운영 장애는 `hotfix/*`로 처리합니다.** `main`에서 따서 `main`으로 병합하고,
**곧바로 `main`을 `dev`로 되병합합니다.** 이걸 빼먹으면 다음 릴리스 때 핫픽스가
되돌아가 같은 장애가 재발합니다. 환경 브랜치 모델에서 가장 자주 나는 사고입니다.

```
장애 발생 → hotfix/xxx (main 에서 분기) → main 병합 → 운영 반영
                                        → main 을 dev 로 되병합  ← 빼먹지 말 것
```

**릴리스는 `dev` → `main` 병합입니다.** 시점을 정해 한 번에 올립니다.

작업 브랜치는 **며칠 안에** 병합합니다. 오래 살수록 충돌이 커집니다.

> 현재 브랜치가 `master`이고 원격이 없습니다. 원격을 붙일 때 `main`으로 바꾸고,
> 지금까지의 커밋을 `main`에 둔 뒤 거기서 `dev`를 냅니다.

### 6.1.1 배포 연결 (원격 붙인 뒤)

`dev` · `main` 푸시를 각 서버 배포에 걸어 둡니다. 구체적인 방법은 배포 형태가 정해진
뒤에 채웁니다 ([TODO.md](../TODO.md) 3단계).

- `dev` 푸시 → 개발 서버 자동 배포
- `main` 푸시 → 운영 서버 배포. **운영은 자동으로 나가지 않게 승인 단계를 둡니다**

### 6.2 커밋 메시지

```
<타입>: <무엇을 했는지 한 줄>

왜 그렇게 했는지. 무엇을 바꿨는지는 diff 를 보면 되지만,
왜 그 선택을 했는지는 여기 없으면 사라진다.
대안이 있었다면 왜 그쪽이 아닌지도 적는다.
```

타입: `feat` `fix` `refactor` `docs` `style` `test` `chore` `perf`

- 제목은 한 줄, 마침표 없이
- 본문은 한글. **무엇이 아니라 왜**를 적습니다
- 한 커밋은 한 가지 일만. 되돌릴 수 있는 단위여야 합니다

### 6.3 PR

- 리뷰어가 한 번에 읽을 수 있는 크기로 자릅니다
- 설명에는 **무엇을 확인해야 하는지**를 적습니다. 코드를 읽으면 아는 것 말고,
  화면을 봐야 아는 것
- 빌드·린트·타입체크가 통과한 상태로 올립니다

## 7. 결정 이력

이 문서의 규칙은 모두 확정됐습니다. 미결 없음.

| 항목 | 결정 | 다시 열 만한 조건 |
|---|---|---|
| 축약어 (1.2) | 거의 금지, 허용 목록만 | 맞춰야 할 외부 시스템·양식이 생기면 |

| 브랜치 (6.1) | 환경 브랜치 (`main` 운영 / `dev` 개발) | 동시 버전 유지가 필요해지면 |

그 결정을 뒤집어도 되는지 알 수 없습니다.
