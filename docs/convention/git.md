# 컨벤션 — git

브랜치 · 커밋 · PR, 그리고 **에이전트가 저장소에 무엇을 해도 되는지**.

표기·식별자 규칙은 [core.md](core.md), 스택 종속 규칙은 [stack.md](stack.md)에 있습니다.

---


## 1. 브랜치 — 환경에 대응시킨다

**브랜치가 곧 배포 대상입니다.** 어디에 병합했는지가 어느 서버에 올라가는지를 결정합니다.

```
main   운영 서버      ← dev 에서 릴리스할 때만 병합
 ↑
dev    개발 서버      ← 기능 브랜치가 모이는 곳
 ↑
feature/tab-workspace     작업 브랜치. 병합 후 삭제
fix/command-dialog
```

| 브랜치 | 대응 | 누가 여기에 병합하나 |
|---|---|---|
| `main` | 운영 서버 | `dev` (릴리스), `hotfix/*` — **둘 다 PR 경유** (3장) |
| `dev` | 개발 서버 | `feature/*`, `fix/*` |
| `feature/*` · `fix/*` | 없음 | 개인 작업 |

접두어는 커밋 타입과 같은 것을 씁니다 — `feature` · `fix` · `refactor` · `docs` · `chore`.
(커밋 타입은 `feat`이지만 브랜치는 `feature`로 풀어 씁니다. 브랜치명은 목록에서 눈으로
읽는 대상이라 줄이는 이득이 없습니다.)

**작업 브랜치는 `dev`에서 따고 `dev`로 돌아갑니다.** `main`에서 따면 `dev`에만 있는
변경을 못 받습니다.

**운영 장애는 `hotfix/*`로 처리합니다.** `main`에서 따서 `main`으로 병합하고,
**곧바로 `main`을 `dev`로 되병합합니다.** 이걸 빼먹으면 다음 릴리스 때 핫픽스가
되돌아가 같은 장애가 재발합니다. 환경 브랜치 모델에서 가장 자주 나는 사고입니다.

```
장애 발생 → hotfix/xxx (main 에서 분기) → main 병합 → 운영 반영
                                        → main 을 dev 로 되병합  ← 빼먹지 말 것
```

**릴리스는 `dev` → `main` PR 입니다.** 시점을 정해 한 번에 올립니다 (3장).

작업 브랜치는 **며칠 안에** 병합합니다. 오래 살수록 충돌이 커집니다.

### 1.1 원격

```
origin   https://github.com/ch00kh/menscake-management-system.git
```

원격 이름은 **`origin`** 입니다. 브랜치명(`main`)과 겹치지 않게 관례를 따릅니다 —
겹치면 `main/main` 같은 참조가 나와 명령을 읽을 때마다 헷갈립니다.

`main` · `dev` 둘 다 원격에 있고 로컬이 각각을 추적합니다.

### 1.2 배포 연결

`dev` · `main` 푸시를 각 서버 배포에 겁니다. 서버는 사내 2대입니다
([stack.md](stack.md) 3장).

- `dev` 푸시 → 개발 서버 자동 배포
- `main` 푸시 → 운영 서버 배포. **운영은 자동으로 나가지 않게 승인 단계를 둡니다**

구체적인 파이프라인은 5단계 착수 때 만듭니다.

## 2. 커밋 메시지

```
<타입>: <무엇을 했는지 한 줄>

왜 그렇게 했는지. 무엇을 바꿨는지는 diff 를 보면 되지만,
왜 그 선택을 했는지는 여기 없으면 사라진다.
대안이 있었다면 왜 그쪽이 아닌지도 적는다.
```

타입: `feat` `fix` `refactor` `docs` `style` `test` `chore` `perf`

- 제목은 한 줄, 마침표 없이
- 본문은 한글. **무엇이 아니라 왜**를 적습니다
- 한 커밋은 한 가지 일만. 되돌릴 수 있는 단위여야 합니다

## 3. PR

### 3.1 언제 PR을 만드나

**`main` 으로 가는 모든 변경은 PR을 거칩니다.** `dev` 는 아닙니다.

| 병합 | PR | 왜 |
|---|---|---|
| `dev` → `main` (릴리스) | **필수** | 운영 서버에 나갑니다 |
| `hotfix/*` → `main` | **필수** | 급할수록 사고가 납니다 |
| `feature/*` · `fix/*` → `dev` | 선택 | 개발 서버라 되돌리는 비용이 낮습니다 |

**운영에 무엇이 왜 나갔는지가 한 자리에 남아야 합니다.** 커밋 로그를 거슬러 올라가며
재구성하는 게 아니라, 릴리스 PR 하나를 열면 보여야 합니다.

핫픽스도 PR을 만듭니다. 다만 **승인을 기다리지 않고 병합해도 됩니다** — 기록이
목적이지 대기가 목적이 아닙니다. 병합 후에 확인합니다.

### 3.2 릴리스 PR 본문

```
## 이번에 나가는 것
기능 단위로. 커밋 목록이 아니라 사람이 읽는 단위로 적습니다.

## 확인해야 하는 것
코드를 읽으면 아는 것 말고, 화면을 봐야 아는 것.

## 마이그레이션
있으면 파일명과 무엇을 바꾸는지. 파괴적 변경이면 그렇다고 적습니다.

## 되돌리는 법
문제가 나면 무엇을 되돌리면 되는지. 마이그레이션이 있으면 그것도.
```

**「되돌리는 법」을 반드시 적습니다.** 운영 배포이고, 마이그레이션은 롤백이 없습니다
([stack.md](stack.md) 4.2). 되돌릴 방법이 안 적히는 릴리스는 되돌릴 방법이 없는
릴리스입니다.

병합 전에 빌드 · 린트 · 타입체크 · 테스트가 통과한 상태여야 합니다.

### 3.3 병합은 merge commit — squash 하지 않습니다

```
git merge --no-ff
```

커밋 본문에 **왜**를 적기로 했습니다(2장). squash 하면 그 본문들이 하나로 뭉개져
**정확히 남기려던 것이 사라집니다.**

`--no-ff` 로 병합하는 이유는 fast-forward 되면 "이 커밋들이 한 덩어리였다"가
안 보이기 때문입니다.

그래서 **병합 커밋 메시지가 곧 릴리스 노트**가 됩니다. 릴리스 PR 본문의
「이번에 나가는 것」을 그대로 씁니다.

병합한 작업 브랜치는 삭제합니다.

### 3.4 크기와 설명

- 리뷰어가 **한 번에 읽을 수 있는 크기**로 자릅니다
- 설명에는 **무엇을 확인해야 하는지**를 적습니다. 코드를 읽으면 아는 것 말고,
  화면을 봐야 아는 것
- **무엇을 안 했는지도 적습니다.** 범위 밖으로 남긴 것, 확인하지 못한 것.
  안 적으면 읽는 사람이 다 됐다고 가정합니다

### 3.5 에이전트가 PR을 만들 때

- **PR 생성과 병합은 승인 대상입니다** (4.1)
- 본문에 **스스로 판단해서 정한 것**을 명시합니다. 지시에 없었는데 정한 것이
  있으면 그게 가장 먼저 확인받아야 할 것입니다
- 확인하지 못한 것을 숨기지 않습니다. "테스트는 돌리지 못했습니다"가
  "테스트 통과"보다 낫습니다

## 4. 에이전트 규칙

개발을 에이전트가 수행합니다. **저장소에 흔적을 남기는 일은 사람이 승인합니다.**

### 4.1 승인 없이 하지 않는 것

```
커밋 · 푸시 · 병합 · 리베이스 · 태그 · PR 생성/병합
브랜치 생성 · 삭제 · 이름 변경
git reset --hard · git checkout -- · stash drop
```

**승인은 그 작업에 대한 명시적 지시입니다.** "커밋해줘" "푸시해줘" 처럼요.
직전 요청에 대한 "좋아" "그렇게 해줘" 는 그 요청의 범위까지이지 커밋 승인이 아닙니다.

한 번 승인이 다음 번으로 이어지지 않습니다. 매번 받습니다.

### 4.2 승인 없이 해도 되는 것

```
파일 생성 · 수정 · 삭제 (작업 트리)
git status · diff · log · show · branch · remote -v
fetch (로컬 상태만 갱신한다)
커밋 메시지 초안 제시
```

작업 트리를 자유롭게 고치되 **커밋하지 않고 멈춰서 보고**합니다.
사람이 `git diff` 로 보고 판단합니다.

### 4.3 왜 이렇게 하나

| | |
|---|---|
| 커밋 단위와 메시지는 판단이다 | 무엇을 한 덩어리로 묶을지, 왜 그렇게 했는지는 사람이 정합니다 |
| 푸시는 되돌리기 어렵다 | 로컬 커밋은 고칠 수 있지만 올라간 것은 남습니다 |
| 잘못 커밋된 개인정보는 히스토리에 남는다 | 이 저장소는 수령인·담당자 정보를 다루는 설계를 담고 있습니다 |

### 4.4 절대 하지 않는 것

**승인을 받아도 하지 않습니다.**

- `git push --force` / `--force-with-lease` — 남의 커밋을 지웁니다.
  되돌려야 하면 `git revert` 로 **새 커밋**을 만듭니다
- `main` 에 직접 커밋 — 릴리스는 PR 로 올립니다 (3.1)
- **squash 병합** — 커밋 본문의 「왜」가 뭉개집니다 (3.3)
- 훅 건너뛰기 (`--no-verify`) — 훅이 막으면 원인을 고칩니다
- 커밋 수정 (`--amend`) 후 푸시 — 이미 올라간 것은 새 커밋으로 고칩니다

### 4.5 커밋할 때 지키는 것

- 한 커밋은 한 가지 일만 (2장)
- 본문에 **왜**를 적습니다 (2장)
- 스테이징은 **경로를 명시**합니다. `git add .` 는 의도하지 않은 파일을 담습니다
- 커밋 전에 `git status` 로 무엇이 담기는지 보고합니다
