## 1. 백업

### 1.1 무엇을 · 언제

| | |
|---|---|
| 대상 | Postgres 전체 (`pg_dump`) + 서버 설정 파일 |
| 주기 | **하루 1회.** 새벽, 주문 업로드 전 |
| 보관 | 일 7세대 · 주 4세대 · 월 6세대 (약 17개) |
| 암호화 | **필수.** 백업 파일 자체를 암호화한 뒤 옮깁니다 |
| 위치 | **사내 NAS** (팀 확인) |

압축하면 한 세대가 500 MB 안팎이라 17세대가 10 GB 미만입니다
([sizing.md](sizing.md) 3장).

### 1.2 하루치를 잃으면 무엇을 잃나

주기를 하루로 잡아도 되는 이유가 설계에 있습니다.

| 잃는 것 | 복구 |
|---|---|
| 주문 · 주문라인 | **채널에서 다시 import 하면 돌아옵니다.** 원본은 채널에 있습니다 |
| 상태 · 담당자 · 메모 | **못 살립니다.** 운영 소유 컬럼입니다 |
| 입고 · 출고 · 실사 전표 | 못 살립니다. 종이 전표가 있으면 다시 입력 |

**진짜 잃는 건 "운영 상태"입니다** — 이 시스템이 존재하는 이유 그 자체입니다.
그래서 시점 복구(WAL 아카이빙)가 필요해지면 그때 붙입니다. 지금은 과합니다.

### 1.3 NAS로 정한 것의 한계

건물 단위 사고(화재 · 침수)에는 서버와 NAS가 **같이 당합니다.** 이건 팀이 알고 고른
것이므로 다시 따지지 않습니다.

다만 값싼 보완책 하나는 적어둡니다 — **월 1회 세대 하나를 사외로 뺍니다.**
암호화된 파일이라 클라우드 스토리지든 물리 매체든 상관없습니다. 월 1회면 최악의
경우 한 달치를 잃지만, 전부 잃는 것보다는 낫습니다.

## 2. 복구 리허설

**분기 1회.** 안 해본 백업은 백업이 아닙니다.

### 2.1 방법

개발 서버가 이미 있으므로 **별도 장비가 필요 없습니다.**

```
1. 운영 백업의 최신 세대를 개발 서버에 복원
2. 익명화 스크립트 실행          ← 2.2. 건너뛰면 안 됩니다
3. 로그인 → 주문 목록 → 재고 현황 → 주문 상세까지 확인
4. 소요 시간을 기록                실제 사고 때 "얼마나 걸리나"의 근거
```

### 2.2 리허설이 만드는 위험

**복원하는 순간 개발 서버에 운영 개인정보가 들어갑니다.** 개발 서버는 보통 운영보다
접근이 헐겁습니다.

그래서 복원 직후 반드시 익명화합니다.

```
sales_order      receiver_name · receiver_phone · receiver_zipcode
                receiver_address · delivery_message  → 더미 값으로 치환
partner_contact  name · phone · email            → 더미 값으로 치환
account         password_hash                    → 개발용 값으로 치환
```

**익명화 스크립트는 백업 스크립트와 같이 관리합니다.** 따로 두면 언젠가 안 돌립니다.

리허설이 끝나면 개발 서버 DB를 원래대로 되돌립니다.

## 3. 접근 통제

### 3.1 DB 계정을 셋으로 나눕니다

| 계정 | 권한 | 쓰는 곳 |
|---|---|---|
| `app` | 테이블 읽기·쓰기. **DDL 없음** | 애플리케이션 |
| `migrator` | DDL 포함 | Flyway 실행 시에만 |
| `ops_*` | 읽기 전용. **사람마다 하나씩** | 운영자 임시 조회 |

**공용 계정을 만들지 않습니다.** `ops_*`를 개인별로 두는 이유는 누가 운영 DB를 직접
봤는지가 남아야 하기 때문입니다.

`app` 계정에서 DDL을 빼는 이유는 애플리케이션 취약점이 스키마까지 가지 못하게
막기 위해서입니다.

### 3.2 서버

```
SSH        키 전용. 비밀번호 로그인 금지. root 직접 로그인 금지
5432       애플리케이션 서버에서만. 사내망이라도 전체 개방 금지
nginx      TLS 필수. 사내 인증서 또는 Let's Encrypt
```

**사내망이니까 괜찮다**는 가정을 두지 않습니다. 개인정보가 있는 DB에 사무실
어느 자리에서나 붙을 수 있으면 통제가 아닙니다.

## 5. 접속기록 `access_log`

**개인정보를 조회한 기록**입니다. 지금까지 설계한 `sales_order_history`는 **바꾼 것**만
남기고 **본 것**은 안 남깁니다. 그 빈자리를 채웁니다.

### 5.1 화면·API 단위로 남깁니다

```
access_log
  id            BIGINT        PK
  account_id    BIGINT        누가. account.id
  accessed_at   TIMESTAMPTZ   언제
  endpoint      VARCHAR       어떤 조회 (API 경로)
  query_params  VARCHAR       조회 조건. 검색어 · 필터 · 페이지
  target_type   VARCHAR       NULL 허용. 한 건을 연 경우 대상 종류
  target_id     BIGINT        NULL 허용. 그 대상 id
  result_count  INT           몇 건이 나왔나
  client_ip     VARCHAR
```

> **append only 입니다.** `updated_at` · `deleted_at` 이 없습니다 —
> `stock_ledger` · `sales_order_history` 와 같습니다.

| 상황 | 남는 것 |
|---|---|
| 주문 목록을 염 | 엔드포인트 · 필터 조건 · 결과 42건 |
| 주문 한 건을 염 | 위 + `target_type = ORDER` · `target_id = 12345` |
| 택배사 엑셀을 내보냄 | `shipment_export` 에 별도로 ([7-shipping.md](domain/7-shipping.md) 4장) |

**행 단위로 남기지 않는 이유**는 목록 한 번 열 때마다 수십 행이 쌓여 접속기록이
주문 테이블보다 커지기 때문입니다. 목록에서 뭘 봤는지는 **조회 조건 + 건수**로
재현됩니다.

### 5.2 조회된 값은 남기지 않습니다

**"누가 언제 무엇을 조회했는가"는 남기고, "조회 결과가 무엇이었는가"는 안 남깁니다.**

파기 로그와 같은 원칙입니다 ([3-partner.md](domain/3-partner.md) 3.2). 접속기록에
개인정보 값을 담으면 **그게 또 하나의 개인정보 사본**이 되고, 파기할 곳이 하나 더
늘어납니다.

### 5.3 보관 기간과 크기

| | |
|---|---|
| 보관 | **2년** (설정값 `accessLogRetentionYears`) |
| 삭제 | 크론이 매일 만료분을 지웁니다. 파기 배치와 같은 자리 |

```
5명 × 하루 100회 × 365일 × 2년 ≈ 36만 행
```

작습니다. 주문 테이블의 절반도 안 됩니다.

### 5.4 위변조 방지

**`app` 계정에 이 테이블의 `DELETE` · `UPDATE` 권한을 주지 않습니다.**

```
app        INSERT · SELECT 만
purger     DELETE 만. 만료분 삭제 크론 전용
```

애플리케이션 코드가 아무리 잘못돼도 접속기록을 지울 수 없어야 기록에 의미가
있습니다. 3.1의 계정 분리가 여기서 한 번 더 쓰입니다.
