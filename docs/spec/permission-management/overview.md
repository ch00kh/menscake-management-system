# 권한 관리 — 개요

## 배경

[계정 관리](../account-management/overview.md)와 [auth 도메인](../auth/overview.md)에서 "별도 이슈로 분리"해뒀던 항목이다. 지금은 계정별 `permission` 행(리소스별 CRUD)이 Flyway 시드 데이터로만 존재해서, 새 계정을 만들어도 권한이 0개라 관리자가 DB를 직접 만지지 않는 한 아무 화면에도 접근하지 못한다.

## 범위

**포함:**
- 계정 관리 화면(`AccountManagementPage`) 리스트의 행 액션에서 모달로 여는 "리소스 x CRUD 권한 매트릭스" 편집 UI — 별도 페이지/라우트를 새로 만들지 않는다
- 권한 부여 대상이 될 수 있는 리소스 키 전체 목록("리소스 화이트리스트")을 백엔드 코드 상수로 정의하고 API로 노출 (지금은 `accounts`, `permissions` 2개)
- 계정에 저장된 `permission` 행이 하나도 없을 때, role에 따른 기본 CRUD 값을 모달을 여는 시점에 화면에만 1회성으로 미리 채워주는 프리필 (저장해야 실제 데이터가 됨)
- 이 화면 자체(조회/저장 API)를 `permissions` 리소스 키로 `@RequiresPermission` 보호 — role이 아니라 기존 auth 도메인의 권한 체크 메커니즘 그대로 사용
- 관리자가 로그인 본인 계정의 `permissions` 리소스 조회/수정 권한을 스스로 없애 자기 자신을 이 화면에서 잠그는 것을 방지("자기잠금 방지")

**제외 (별도 이슈로 분리):**
- 계정 생성 시 서버가 자동으로 기본 `permission` 행을 만들어주는 기능 — 지금은 화면을 열 때 프론트에서만 계산하는 프리필로 충분 (YAGNI)
- 다른 계정의 권한을 복사해오는 기능, role별 권한 프리셋을 관리하는 별도 화면 — 지금 규모에서는 불필요
- 실제 업무 리소스(주문/재고 등)가 생길 때 리소스 화이트리스트에 항목을 추가하는 작업 — 그 리소스를 만드는 이슈에서 함께 처리
