# Agent Collaboration

## 작업 할당

- **이슈는 사람이 직접 작성한다** (`.github/ISSUE_TEMPLATE/task.yml`). 에이전트는 이슈를 생성하지 않는다 — 작업 단위별로 에이전트가 이슈를 만들던 방식은 병목만 되고 실효가 없어 폐지했다 (GitHub Projects 보드도 같은 이유로 삭제).
- 메인 세션은 열린 이슈를 확인하고, 그 내용을 처리할 서브에이전트를 띄운다.
- 새 기능/도메인 설계처럼 브레인스토밍이 필요한 작업은 이슈 유무와 무관하게 아래 "기능 개발 흐름"을 따른다. 스펙 문서(`docs/spec/<도메인>/`)가 "무엇을 만들지"에 대한 단일 진실 공급원(SSOT)이다.
- 이슈도 스펙도 없는 작은 버그 수정/설정 변경은 브랜치+PR만으로 바로 진행한다.

## 기능 개발 흐름

1. **브레인스토밍 + 스펙 작성**: `dev`에서 분기한 문서 전용 브랜치에서 인터뷰를 거쳐 `docs/spec/<도메인>/` 스펙 문서를 작성하고, PR을 올려 `dev`에 머지까지 마친다.
2. **구현**: 스펙이 `dev`에 반영된 뒤, 프론트엔드/백엔드 서브에이전트를 띄워 구현을 진행한다 (병렬 가능 여부는 아래 "병렬 실행 가능성 판단" 참조). 각 서브에이전트는 자기 브랜치에서 작업해 PR까지 올린다.
3. **머지**: 서브에이전트는 자신의 PR을 직접 머지하지 않는다 — 메인 세션이 결과를 받아 검토(런타임 동작이 있으면 사람의 직접 테스트도 거쳐) 후 머지한다.

## 브랜치/PR이 필요한 경우

- **개발(코드) 변경** — `apps/web`, `apps/api` 등 실제 애플리케이션 코드를 건드리는 작업은 위 "기능 개발 흐름"과 브랜치+PR 규칙을 그대로 따른다.
- **그 외(문서, 프로세스, 툴링/설정)** — `docs/`, `.claude/`, `.github/` 템플릿처럼 애플리케이션 코드가 아닌 변경은 메인 세션이 별도 브랜치나 PR 없이 `dev`에 직접 커밋·push한다. `dev` 브랜치 보호는 `enforce_admins`가 꺼져 있어 관리자 계정은 PR 없이 직접 push할 수 있다 (`docs/rule/git-convention.md` 참조).

## 병렬 실행 가능성 판단

- 스펙(`docs/spec/<도메인>/`)이 확정되고 나서 구현을 여러 갈래(예: api/web)로 나눌 때, 각 갈래를 시작하는 시점에 **서로 독립적으로 병렬 실행이 가능한지** 판단하고 PR 본문에 한 줄로 명시한다.
  - **병렬 가능**: 다른 쪽의 실제 구현체 없이 스펙 문서(API 계약 등)만으로 작업을 끝낼 수 있는 경우.
  - **병렬 불가능**: 한쪽이 실제로 동작하는 상대쪽 결과물(엔드포인트, 배포본 등)이 있어야 완료/검증할 수 있는 경우 — 이땐 순서와 이유를 PR 본문에 적는다.
- **병렬 가능으로 판단되면 실제로 병렬로 실행한다** — Agent 툴로 갈래마다 서브에이전트를 동시에 띄운다. "가능하다고 적어만 놓고 순차로 진행"하지 않는다.
- 애매하면 가정하지 말고(아래 "가정 절대 금지" 원칙) 병렬 불가능 쪽으로 보수적으로 판단한다.

## 모호함 처리 — 가정 절대 금지

- **요구사항이 모호하면 추측·가정으로 진행하지 않는다.** "합리적으로 보이는 가정"도 예외 없이 금지한다.
- 반드시 사용자에게 직접 질문하고, 응답이 올 때까지 작업을 중단하고 대기한다.
- 잘못된 가정으로 진행한 작업을 되돌리는 비용이, 질문하고 기다리는 비용보다 항상 크다.

## 작업 시작 전 체크리스트

1. `dev` 최신으로 pull
2. 관련 스펙 문서(`docs/spec/<도메인>/`, 있다면) 정독
3. `docs/rule/` 컨벤션 문서 확인
4. git-convention 네이밍대로 `dev`에서 새 브랜치 생성

## 작업 종료 후 체크리스트 (PR 올리기 전)

1. 로컬 lint/test 통과 확인
2. 스스로 diff 리뷰 (불필요한 파일 변경 없는지)
3. PR 제목 = 커밋 컨벤션 형식, 본문에 관련 이슈(`Closes #`) 또는 스펙 문서 경로(있는 쪽)와 어떤 작업으로 생성됐는지 한 줄 요약
4. **런타임 동작이 있는 변경(화면, API 응답 등)은 머지 전에 사람이 직접 실행해서 확인받는다.** 문서·설정처럼 동작 확인이 사실상 불가능하거나 lint/test만으로 충분히 검증되는 변경은 승인 대기 없이 바로 머지한다 (`git-convention.md`의 1인 관리자 예외 참조). CI가 실패했거나 diff에 이상한 점이 보이면 머지하지 말고 먼저 확인한다.

## 컨벤션 문서 자체가 SSOT

- `docs/rule/` 문서가 프로젝트 규칙의 SSOT다.
- 코드/PR에서 문서와 다른 방식을 발견해도 임의로 새 패턴을 만들지 않는다. 먼저 `docs/rule/`을 확인하고, 문서에 없는 규칙이 필요하면 문서 추가를 먼저 제안한다.
