# 데이터 규모와 부하 추정

기술 스택을 고르기 전에 **얼마나 커지는지**를 계산합니다. 이 숫자가 없으면 DB · 호스팅 ·
페이징 · 배치 선택이 전부 취향 싸움이 됩니다.

도메인 설계는 [domain/](domain/), 다음 단계는 [TODO.md](../TODO.md) 3단계입니다.

---

## 1. 입력값

| 항목 | 값 | 출처 |
|---|---|---|
| 일 주문 건수 | **100~500건** | 팀 확인 |
| SKU (옵션조합) 수 | **500~3,000개** | 팀 확인 |
| 판매처 수 | **1~3개** | 팀 확인 |
| 사용자 수 | 5명 이상, 교대 근무 | [domain/scope.md](domain/scope.md) 1장 |
| 동시 접속 | 보통 1~2명, 피크 3명 | **추정.** 교대제에서 도출 |

**아래 계산은 전부 상한값(500건 · 3,000 SKU)으로 합니다.** 하한으로 잡으면 스택을
고르고 나서 모자랍니다.

### 1.1 가정

| 가정 | 값 | 근거 |
|---|---|---|
| 영업일 | 365일 | 쇼핑몰은 주말에도 주문이 들어옵니다 |
| 주문당 라인 수 | 1.5줄 | 일반적인 쇼핑몰 평균. **실측으로 교체할 것** |
| 주문당 이력 행 | 5행 | 상태 3전이 + 담당자 배정 + 재import 변경 |
| 보관 기간 | 5년 | 수령인 파기 기준과 동일 ([domain/6-order.md](domain/6-order.md) 7장) |

## 2. 5년 뒤 행 수

```
연간 주문 = 500 × 365 = 182,500건
```

| 테이블 | 연간 | 5년 누적 |
|---|---|---|
| `sales_order_history` | 91만 | **456만** |
| `stock_ledger` | 37만 | **185만** |
| `sales_order_line` | 27만 | **137만** |
| `sales_order` | 18만 | **91만** |
| 나머지 전부 | — | 10만 미만 |
| **합계** | | **약 870만 행** |

`stock_ledger` 내역

```
출고    sales_order_line 137만 × 세트 전개 1.2 = 164만
입고    SKU 3,000 × 연 12회 × 5년       =  18만
실사·조정·기부폐기                        =   3만
```

`stock`(현재고)은 `SKU 3,000 × 창고 1 × 활성 로트`라 **6,000행** 수준입니다. 원장이
아무리 쌓여도 현재고 테이블은 안 큽니다 — 4번에서 캐시를 따로 둔 구조의 이득입니다.

## 3. 용량

| 테이블 | 행 크기 | 5년 |
|---|---|---|
| `sales_order` | ~1.5 KB | **1.4 GB** |
| `sales_order_history` | ~200 B | 0.9 GB |
| `sales_order_line` | ~300 B | 0.4 GB |
| `stock_ledger` | ~150 B | 0.3 GB |
| 소계 | | 3.0 GB |
| 인덱스 (×1.5) | | **약 4.5 GB** |

### 3.1 `raw_data`가 용량의 절반입니다

`sales_order` 행이 1.5 KB인 건 **`raw_data` 하나 때문**입니다. 나머지 컬럼을 다 합쳐도
500 B가 안 됩니다.

채널 엑셀 한 줄을 (수령인 열을 뺀 채로) 그대로 담기로 한 결정
([domain/6-order.md](domain/6-order.md) 1장)의 비용입니다. 매핑 실수를 복구할 수
있다는 값어치가 있으니 지금은 그대로 갑니다.

**다만 용량이 문제가 되면 여기가 첫 번째로 손볼 곳입니다.** 손보는 방법도 정해뒀습니다 —
오래된 주문의 `raw_data`만 비우면 됩니다. 파생 데이터라 지워도 주문은 멀쩡합니다.

## 4. 결론 — 스택 선택에 넘기는 것

### 4.1 필요 없는 것

| | 왜 |
|---|---|
| 샤딩 · 파티셔닝 | 5년 870만 행 · 4.5 GB. 단일 인스턴스로 여유 |
| 캐시 계층(Redis 등) | 동시 3명. 캐시가 해결할 경합이 없음 |
| 검색 엔진 | SKU 3,000 · 주문 91만. 인덱스 + `LIKE` 로 충분 |
| 무거운 잡 큐 | 배치가 개인정보 파기 2건 + 안전재고 알림뿐. 크론 수준 |
| 비관적 잠금 | 동시 1~2명. 낙관적 잠금이 맞습니다 ([6-order.md](domain/6-order.md) 6장) |
| 가상 스크롤 | 화면당 최대 6,000행(재고 현황). 서버 페이징이면 충분 |

### 4.2 필요한 것

| | 왜 |
|---|---|
| **서버 페이징** | 주문 목록이 5년 91만 행. 클라이언트 전체 로드 불가 |
| **인덱스 설계** | `sales_order (channel_id, channel_order_no)` `(status, ordered_at)`, `stock_ledger (variant_id, warehouse_id, lot_id, moved_at)` 최소 이것들 |
| **트랜잭션** | 입고·출고·실사 확정이 원장·현재고·전표를 한 번에 바꿉니다 |
| **부분 유니크 인덱스** | 3건. [TODO.md](../TODO.md) 4단계 |
| **엑셀 파싱(서버)** | 위저드 2단계에서 전체를 읽어 검증해야 합니다 |
| **크론** | 개인정보 자동 파기 2건 |

### 4.3 업로드 피크

하루 부하가 몰리는 유일한 지점입니다.

```
매일 아침  판매처 1~3개 × 500행 = 최대 1,500행
대부분 UPDATE (재import)
```

**1,500행이면 동기 처리로 몇 초입니다.** 비동기 배치가 필요 없습니다. 다만 위저드
2단계(미리보기)가 커밋 전에 전체를 검증하므로, 파싱과 검증은 서버에서 하고 결과만
넘깁니다.

## 5. 재검토 트리거

이 문서는 **지금 규모의 스냅샷**입니다. 아래 중 하나라도 넘으면 다시 계산합니다.

```
일 주문 2,000건 초과      → 원장이 천만 행대. 파티셔닝 검토
DB 20 GB 초과             → raw_data 정리부터
SKU 10,000 초과           → 매핑·재고 화면에 가상화 필요
동시 접속 10명 초과        → 낙관적 잠금 재검토
판매처 9개 초과            → 채널 API 연동 검토 ([5-channel.md](domain/5-channel.md) 1.1)
```

## 6. 실측으로 교체할 것

추정에 쓴 두 숫자는 **관측값이 아닙니다.**

```
주문당 라인 수 1.5    첫 import 후 실제 평균으로 교체
주문당 이력 행 5      3개월 운영 후 실제 값으로 교체
```

둘 다 결과를 크게 흔들지는 않습니다 — 라인 수가 3줄이어도 총량이 1.3배이고, 여전히
단일 DB 범위입니다. 그래도 숫자의 출처는 적어둡니다.
