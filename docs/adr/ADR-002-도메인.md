## 2.1 주문 취합이 목적이지만 도메인을 아래에서 위로 쌓는다

### 배경

팀이 실제로 아픈 곳은 6번 주문인데, 거기 닿으려면 앞에 도메인 넷이 필요합니다.
이전 초안은 v1을 "주문 취합 하나"로 잡고 상품을 자유 텍스트(`sku_raw`)로 두었고,
채널 간 SKU 매칭은 v2로 미뤄져 있었습니다.

### 결정

```
1 사용자·권한 → 2 상품 → 3 거래처 → 4 입고
              → 5 판매채널 → 6 주문 → 7 출고·송장 → 8 재고 → 9 기부·폐기
```

**주문 취합이 늦어지는 것을 감수합니다.**

### 검토한 대안

| 대안 | 기각 사유 |
|---|---|
| 주문부터 만들고 나머지는 나중에 | 주문 라인이 참조할 상품 마스터가 없어 자유 텍스트가 됩니다. 초안이 그래서 SKU 매칭을 v2로 미뤘습니다 |
| 상품과 주문만 먼저 | 입고 없이 재고가 안 움직여 "재고가 왜 이 숫자냐"에 답할 수 없습니다 |

### 결과

- 그동안 팀은 시트 + 디스코드를 계속 씁니다. **이건 비용입니다**
- 대신 주문 라인이 처음부터 `product_variant` 를 참조합니다
- 9번은 설계 도중 추가됐습니다 (2.19)

## 2.2 권한은 (역할, 메뉴, 행위) 한 줄로 표현한다

> [1-user.md](../domain/1-user.md)

### 결정

```
account ──< account_role >── role ──< role_menu_permission >── menu
                                            └ READ / CREATE / UPDATE / DELETE
```

- 사용자 ↔ 역할은 **N:M**. 유효 권한은 **합집합**
- **행이 있으면 허용, 없으면 거부.** 거부(deny) 행을 두지 않습니다
- `role_code = 'ADMIN'` 은 코드 고정. 검사를 건너뛰고 **활성 사용자가 0명이 되는
  변경을 거부**합니다
- 로그인 식별자는 **아이디**입니다. 관리자가 발급하고 이메일은 선택 정보입니다

### 검토한 대안

| 대안 | 기각 사유 |
|---|---|
| 행위를 컬럼으로 (`can_create` …) | 승인·내보내기가 생길 때마다 컬럼이 늘고 스키마가 바뀝니다 |
| 역할 하나만 배정 | 겸직이 흔합니다. 조합을 못 만들면 역할 수가 폭발합니다 |
| deny 행 허용 | 합집합에 deny 가 섞이면 우선순위 규칙이 필요해지고, 그때부터 **"왜 이 메뉴가 안 보이지"를 아무도 못 풉니다** |
| 로그인을 이메일로 | 메일 없는 인력이 계정을 못 만듭니다 |

### 결과

- 행위가 값이라 `가져오기` `내보내기` `승인` 이 생겨도 테이블 모양이 그대로입니다
- **화면에서 버튼을 숨기는 건 UX이지 보안이 아닙니다.** 서버가 매 요청마다 다시
  검사합니다
- 퇴사는 `active = false` 이지 삭제가 아닙니다 — 감사 컬럼이 `account.id` 를
  참조하므로 행을 지우면 과거 전표의 담당자가 사라집니다.
  이 요구가 [ADR-003](ADR-003-기술스택.md) 3.4의 인증 방식을 정했습니다

## 2.3 메뉴는 DB가 마스터, `menu_code` 는 불변

### 배경

권한이 메뉴에 붙으니 메뉴가 어디서 오는지를 정해야 합니다. 지금 사이드바는
`registry.ts` 라는 코드 파일에서 메뉴를 만듭니다.

### 결정

**DB의 `menu` 테이블이 마스터**입니다. 대신 규칙 둘이 따라옵니다.

1. **`menu_code` 는 불변.** 재사용하면 **지운 메뉴의 권한이 새 메뉴에 그대로 붙습니다**
2. **화면은 코드에 있습니다.** `path` 가 가리키는 화면이 없으면 렌더링하지 않고
   경고 로그만 남깁니다

### 검토한 대안

| 대안 | 기각 사유 |
|---|---|
| 코드가 마스터, DB는 권한만 | 메뉴 하나 늘릴 때마다 배포가 필요합니다 |
| 코드가 정의하고 DB로 동기화 | 유연하지만 동기화 코드가 하나 더 생깁니다 |

### 결과

- 메뉴를 먼저 만들고 화면을 나중에 붙일 수 있습니다. 반대로 화면을 지워도 앱이
  안 죽습니다
- **2.12는 방향이 반대입니다.** 무엇이 바뀌느냐가 다릅니다

## 2.4 상품은 3층 — 상품 · 옵션명/값 · 옵션조합

> [2-product.md](../domain/2-product.md)

### 배경

재고가 깎이고 주문 한 줄이 가리키는 단위 — **SKU가 무엇이냐**를 정하는 문제입니다.
채널이 주는 엑셀은 `색상: 빨강 / 사이즈: L` 같은 문자열입니다.

### 결정

```
상품 ─ 상품옵션 ─ 옵션명 ─ 옵션값
  └──< 옵션조합(product_variant) ──< 조합옵션값
```

- **옵션명·옵션값은 전역 마스터**입니다
- **입고 · 주문 라인 · 재고는 전부 `product_variant.id` 를 참조합니다**
- 분류는 **계층 카테고리(단일 소속) + 태그(다중)** 둘 다 둡니다

### 검토한 대안

| 대안 | 기각 사유 |
|---|---|
| 2층 (옵션은 조합 행의 텍스트) | "빨강 전체 판매량" 집계에 옵션값을 다시 쪼개야 합니다 |
| 1층 (상품 = SKU) | 상품 목록이 수백 줄로 불고 "같은 상품의 다른 색"을 묶을 수 없습니다 |
| 옵션명·값을 상품마다 따로 | 3층으로 간 이유(오타 방지·집계)가 그대로 사라집니다 |

### 결과

- `sort_order` 덕에 사이즈가 **S · M · L** 로 나옵니다. 가나다순(L·M·S)이 아닙니다
- **`option_label` 은 의도적인 중복입니다.** 정규화하면 조합 하나 보는 데 3테이블
  조인인데, 주문 취합은 채널 문자열과 이 값을 **사람이 눈으로 대조**하는 게 작업입니다
- **상품에 기본 공급처와 가격을 두지 않습니다.** 공급처는 입고 전표(4번), 가격은
  채널(5번)과 입고 시점(4번)에 있습니다. 마스터에 박으면 반드시 실제와 틀어집니다

## 2.5 세트는 자기 재고를 갖지 않는다

### 배경

「크림 2개 + 파우치 1개 기획세트」처럼 채널에서는 한 줄로 팔리지만 재고는 여러
SKU에서 깎여야 하는 상품이 있습니다.

### 결정

- 세트 조합이 구성품 조합을 수량과 함께 가리킵니다 (`product_set_item`)
- **세트는 자기 재고를 갖지 않습니다.** 출고 확정 때 구성품으로 전개해 차감합니다
- **세트가 세트를 담을 수 없습니다.** 1단계만
- 판매 가능 수량은 저장하지 않고 `min(구성품 재고 ÷ 구성 수량)` 으로 계산합니다

### 검토한 대안

| 대안 | 기각 사유 |
|---|---|
| 세트도 일반 SKU로 두고 재고를 따로 | 단품과 세트가 **같은 물건을 두 줄로 세게** 되어 결품이 납니다 |
| 8번 재고 설계 때 정하기 | 그때는 이미 4번 입고와 6번 주문이 만들어져 있습니다 |
| 다단계 세트 허용 | 수량이 안 맞을 때 어디서 틀어졌는지 아무도 못 찾습니다 |

### 결과

- 실사·안전재고·기부폐기 대상이 아닙니다
- 세트 전개는 **출고 확정 한 곳에서만** 일어납니다

## 2.6 업무코드는 비우면 자동, 적으면 그대로

### 배경

팀은 구글 시트에 이미 쓰던 상품 코드가 있습니다. 전부 새로 발급하면 시트·발주서·
채널에 있던 코드를 다시 붙여야 합니다.

### 결정

```
비우면   규칙대로 자동 채번 (P00000001 · P00000001-01 · C000001 …)
적으면   그대로 사용
어느 쪽이든   고유성 검사 + 등록 후 변경 불가
```

자동 채번은 이미 쓰인 값을 건너뜁니다.

### 검토한 대안

| 대안 | 기각 사유 |
|---|---|
| 항상 자동 채번 | 이사 시점에 기존 코드를 전부 다시 붙여야 합니다 |
| 항상 수기 입력 | 사람마다 규칙이 달라져 1년 뒤 알아볼 수 없는 코드가 생깁니다 |

### 결과

- 코드 모양이 두 가지로 섞입니다. **감수한 비용입니다**
- `sku_code` 에 상품코드를 넣어 발주서에서 코드만 보고 어느 상품인지 압니다

## 2.7 재고는 원장이 진실이고 현재고는 캐시다

> [4-receiving.md](../domain/4-receiving.md) 2장 · [8-stock.md](../domain/8-stock.md)

### 배경

통장에는 **거래내역**과 **잔액**이 있습니다. 재고도 같습니다. 지금 시트는 잔액만
들고 있어서 숫자가 틀리면 언제 왜 틀렸는지 알 수 없습니다.

### 결정

**둘 다 둡니다.**

```
stock_ledger   append only. 수량이 움직인 기록. 진실
stock          원장의 합계. 캐시. 재계산 가능
```

수량을 건드리는 **모든 도메인이 같은 문 하나를 지납니다** —
입고 · 출고 · 실사 · 조정 · 기부폐기.

### 검토한 대안

| 대안 | 기각 사유 |
|---|---|
| 잔액만 | 숫자가 틀렸을 때 추적할 방법이 없습니다. **지금 시트와 같은 상태** |
| 내역만 (매번 합산) | 어긋날 일이 없지만 연차가 쌓이면 조회가 점점 느려집니다 |

### 결과

- **8번 재고의 범위가 여기서 확정됐습니다** — 테이블은 4번 것이고 8번은 같은
  테이블에 성격이 다른 행을 씁니다. 같은 수량을 두 곳에서 관리하지 않습니다
- 원장이 185만 행이 되어도 `stock` 은 6,000행입니다
- 캐시가 틀어졌을 때 **사람이 손으로 숫자를 고치는 순간 원장은 의미가 없어집니다**
- 「재고 이동 내역」 화면이 이 프로젝트의 결론입니다. "빨강L이 왜 6개죠?"에
  화면이 답합니다

## 2.8 확정된 전표는 수정하지 않고 역분개로 취소한다

### 결정

```
작성중(DRAFT) → 확정(CONFIRMED) → 취소(CANCELED)
```

- **작성중 전표는 재고에 아무 영향이 없습니다**
- **확정된 전표는 수정할 수 없습니다.** 취소하고 다시 씁니다
- 취소는 원장에 **반대 부호 행**을 씁니다 (`reversal_of_id` 에 원본 id).
  원본 행도 원본 전표도 지우지 않습니다

### 검토한 대안

| 대안 | 기각 사유 |
|---|---|
| 확정 후에도 수정 허용 | 재고가 이미 움직였는데 무엇을 되돌릴지 규칙이 필요해집니다 |
| 취소 시 원장 행 삭제 | 통장에서 거래를 지우는 것과 같습니다. 감사 추적이 끊깁니다 |

### 결과

- "3월 5일에 10개 받았다가 3월 6일에 취소했다"가 그대로 보입니다
- 입고 · 출고 · 실사 · 조정 · 기부폐기가 **전부 같은 규칙**을 씁니다
- 송장번호와 기부금영수증 번호는 취소해도 **지우지 않습니다.** 실제로 발행됐을 수
  있고, 지우면 그 사실을 추적할 수 없습니다

## 2.9 창고와 로트는 구조만 미리 둔다

### 배경

지금은 물건을 한 곳에 두고 있고, 유통기한 관리도 일부 상품에만 필요합니다.
그런데 **재고를 세는 기준을 나중에 바꾸는 건 특히 어렵습니다.**

### 결정

| | 구조 | 지금 데이터 |
|---|---|---|
| 창고 | `warehouse` 테이블. 재고 키에 포함 | **「기본창고」 한 행만.** 화면에 선택이 안 보임 |
| 로트 | `lot` 테이블. `product.use_lot` 스위치 | 켠 상품만 로트 단위로 셈 |

### 검토한 대안

| 대안 | 기각 사유 |
|---|---|
| 창고 개념 없이 상품당 수량 하나 | 창고가 둘이 되는 날 재고·입고·출고를 전부 고쳐야 하는데 그땐 실제 데이터가 쌓여 있습니다 |
| 모든 상품을 로트 단위로 | 기한 없는 상품까지 입고마다 줄이 늘어 재고 화면이 복잡해집니다 |
| 로트 없이 기한을 메모로만 | "임박한 거 몇 개 남았지"를 시스템이 답하지 못합니다 |

### 결과

- 창고가 늘면 행을 하나 더 넣고 선택 컨트롤을 켜면 됩니다
- `sellable` 컬럼을 미리 넣었습니다 — **반품 재고가 판매 가능 재고에 섞이면
  없는 물건을 팝니다**
- 로트 상품은 출고 시 **사용기한이 빠른 것부터** 자동으로 빠집니다

## 2.10 현장을 막지 않는다 — 발주 초과와 재고 부족은 경고만

### 배경

도입 초기에는 시스템 숫자만 틀린 경우가 반드시 생깁니다 — 입고를 안 적었거나
시트 시절 재고를 넘길 때 틀렸거나.

### 결정

| 상황 | 처리 |
|---|---|
| 발주 잔여를 초과하는 입고 | **경고만 하고 허용.** 도매상이 더 보내는 일이 실제로 있습니다 |
| 재고가 모자란 출고 | **경고하고 보내되** 음수가 난 SKU를 「재고 확인 필요」에 올림 |

### 검토한 대안

| 대안 | 기각 사유 |
|---|---|
| 막는다 | 담당자는 물건이 눈앞에 있는데 못 보내고, **시스템을 우회해서 보냅니다.** 그때부터 기록이 끊기고 재고는 더 틀어집니다 |
| 아무 말 없이 진행 | 언제부터 틀렸는지 아무도 모르게 됩니다 |

### 결과

- 물건은 나가고 숫자는 8번 실사로 맞춥니다
- **막힌 현장은 시스템을 버립니다.** 이게 이 프로젝트에서 반복해서 적용한 판단입니다

## 2.11 채널 미매핑 주문은 받아놓고 소급 연결한다

> [5-channel.md](../domain/5-channel.md)

### 배경

채널은 `상품번호 123456 / 색상: 빨강, 사이즈: L` 같은 문자열을 줍니다. 새 상품을
올리거나 채널에서 옵션명을 고치면 **반드시 매핑이 없는 줄이 나옵니다.**

### 결정

주문은 받아들이되 그 줄은 **「상품 미확인」**(`variant_id is null`)으로 표시하고
전용 화면에 모읍니다. 담당자가 SKU를 붙이면

1. `channel_product_map` 에 행 생성
2. **같은 (판매처, 상품코드, 옵션문자열)을 가진 미확인 주문 라인을 전부 소급 연결**

### 검토한 대안

| 대안 | 기각 사유 |
|---|---|
| 매핑 없으면 업로드 거부 | 신상품 올린 날 아침에 주문을 하나도 못 받습니다. 급하면 다시 시트로 도망갑니다 |
| 문자열만 저장하고 나중에 | "나중"을 재촉하는 게 없어 재고가 안 깎인 줄이 쌓입니다 |

### 결과

- **소급 연결이 핵심입니다.** 매번 손으로 붙이게 하면 사람이 금방 안 하고 화면이 죽습니다
- 미확인 상태에서 주문 접수·조회는 되고 **출고·송장·재고 차감은 안 됩니다**
- `channel_option_text` 는 매핑 키만 정규화합니다 (공백·전각).
  안 하면 `"빨강 / L"` 과 `"빨강/L"` 이 다른 매핑이 되어 두 번 뜹니다

## 2.12 엑셀 열 이름은 DB에, 항목 키는 코드에

### 배경

채널은 예고 없이 열 이름을 바꿉니다 — 「수량」이 「주문수량」으로. 그럼 업로드가
깨집니다.

### 결정

| | 누가 바꾸나 | 어디에 |
|---|---|---|
| `field_key` 우리 항목 | 개발자. 주문 테이블 컬럼이라 코드 없이는 못 늘림 | **코드** |
| `column_name` 엑셀 헤더 | 채널이 예고 없이 바꿈 | **DB** |

**바뀌는 쪽만 DB에 둡니다.** 2.3(메뉴)과 방향이 반대인 이유가 이것입니다.

### 검토한 대안

| 대안 | 기각 사유 |
|---|---|
| 채널별 양식을 코드 상수로 | 양식이 바뀐 날 개발자가 붙을 때까지 주문을 못 받습니다 |
| 업로드할 때마다 사람이 고름 | 매일 아침 같은 작업을 반복하고, 사람마다 다르게 짝지어 주문이 엉뚱하게 들어옵니다 |

### 결과

- "수량"이 "주문수량"으로 바뀌어도 담당자가 화면에서 고치면 그날 복구됩니다
- 필수 항목이 매핑되지 않은 판매처는 **업로드 버튼이 잠깁니다**
- 택배사 양식도 같은 구조입니다. `direction`(가져오기/내보내기)만 하나 늘었습니다

## 2.13 개인정보는 테이블마다 다른 규칙으로 파기한다

> [convention.md](../convention.md) 4.3이 "2단계에서 테이블별로 지정"으로 미뤄둔 항목

### 결정

| 테이블 | 규칙 |
|---|---|
| `partner_contact` 거래처 담당자 | **`deleted_at` 없음. 물리 삭제.** 거래처 미사용 후 3년(설정값) |
| `sales_order` 수령인 5종 | **행은 남기고 컬럼만 NULL로.** 출고완료 후 5년(설정값) |

**두 규칙이 다른 이유** — 거래처 담당자는 행 전체가 개인정보지만, 주문은 행 안의
다섯 칸만 개인정보이고 나머지(금액·상품·수량)는 집계에 계속 필요합니다.

파기 로그에는 **누가·언제·몇 건**만 남깁니다. 지운 값은 안 남깁니다.

### 검토한 대안

| 대안 | 기각 사유 |
|---|---|
| 논리 삭제 + 마스킹 | 값이 그대로 남아 있어 **파기가 아닙니다** |
| 주문 행을 통째로 삭제 | "작년 대비 매출" 같은 집계가 어느 순간부터 틀립니다 |
| 6번에서 한꺼번에 정하기 | 3~5번 도메인을 만드는 동안 이 테이블만 규칙 없이 굴러갑니다 |

### 결과

- **`receiver_purged_at` 이 있으면 재import 가 수령인을 덮어쓰지 않습니다.**
  이 예외가 없으면 옛날 파일 재업로드가 파기한 개인정보를 되살립니다
- **파기 대상은 이력에도 남기지 않습니다.** 그래서 변경 이력 기록 항목이
  화이트리스트입니다
- 내보내기 파일에도 안 남깁니다 — `shipment_export` 는 건수만 기록합니다
- 자동 파기는 배치가 필요합니다. 그때까지는 「파기 예정」 필터로 수동 처리합니다

## 2.14 주문 상태는 5개, 취소는 별도 축

> [6-order.md](../domain/6-order.md)

### 결정

```
접수 ──→ 확인 ──→ 출고대기 ──→ 출고완료
 └────────┴─────────┴──→ 보류 ──→ (되돌아올 수 있음)
```

**취소는 상태 목록에 없습니다.** 우리가 정하는 게 아니라 채널이 알려주는 사실이라
`canceled_at` 컬럼으로 둡니다.

- `SHIPPED` 는 **7번 출고 확정으로만** 도달합니다. 사람이 직접 못 고칩니다
- `READY` 는 상품 미확인이 없고 취소가 아닐 때만

### 검토한 대안

| 대안 | 기각 사유 |
|---|---|
| 3개 (접수/처리중/완료) | 「처리중」이 너무 넓어 품절로 멈춘 건과 송장만 남은 건이 섞입니다 |
| 화면에서 관리자가 추가·수정 | "이 상태면 출고 가능" 판단이 코드에 있어서, 상태를 하나 추가하면 시스템이 그걸 어떻게 다뤄야 하는지 모릅니다 |
| 취소를 상태 값으로 | "확인까지 했는데 취소된 주문"을 표현할 수 없습니다. **그게 정확히 사고가 나는 지점**입니다 |

### 결과

- `SHIPPED` 를 손으로 못 바꾸게 한 덕에 **재고가 안 깎인 채 출고완료가 되는 일이
  없습니다**
- 발주 상태도 같은 원칙입니다 — 입고량에 따라 자동 계산되고 사람이 안 고릅니다.
  **사람이 상태를 관리하는 순간 "이거 처리했어요?"가 돌아옵니다**

## 2.15 재import 는 채널 소유 컬럼만 덮어쓴다

### 배경

같은 채널의 엑셀은 매일 다시 올라옵니다. 무엇을 덮어쓰고 무엇을 지킬지가 이
도메인에서 가장 자주 사고가 나는 곳입니다.

### 결정

| 소유 | 컬럼 | 재import 시 |
|---|---|---|
| 채널 | `channel_status` `ordered_at` `order_amount` `raw_data`, 수령인 5종, 라인의 채널 필드 | **덮어씀** |
| 운영 | `status` `assignee_id` `memo` `canceled_at` `needs_review` | **지킴** |
| 파생 | `variant_id` `variant_quantity` | 매핑에서 다시 계산 |

라인은 **전삭제하지 않고 `match_key` 로 찾아 갱신**합니다.

### 검토한 대안

| 대안 | 기각 사유 |
|---|---|
| 전부 덮어쓰기 | 담당자가 아침에 확인해둔 20건이 오후에 접수로 돌아갑니다. **그날부터 아무도 안 씁니다** |
| 라인을 전삭제·재삽입 | 나중에 부분출고를 하려면 주문 줄 구조를 통째로 다시 짜야 합니다 |

### 결과

- 부분출고는 지금 안 하지만 **문은 열어뒀습니다** — `match_key` 가 안정적 키입니다
- 이번 파일에 없는 기존 라인도 지우지 않습니다. 2.16과 같은 이유입니다

## 2.16 취소 감지는 집합 소속이 아니라 상태 전이다

### 결정

```
channel_status 가 그 판매처의 취소 문자열 집합에 속하고
AND canceled_at IS NULL 이면
→ canceled_at = 지금
```

그리고 **직전 배치엔 있었는데 이번에 없는 주문은 자동 취소하지 않습니다.**
`needs_review = true` 로 「오늘 할 일」에 띄웁니다.

### 검토한 대안

| 대안 | 기각 사유 |
|---|---|
| `canceled_at IS NULL` 조건 없이 | 이미 취소된 주문이 재import 마다 다시 발화하고 **`canceled_at` 이 매번 오늘로 갱신**됩니다 |
| 안 보이는 행을 자동 취소 | 엑셀 export 기간 필터를 잘못 잡아도 행이 사라집니다. **없어진 것과 취소된 것은 다릅니다** |
| 취소 문자열을 코드에 하드코딩 | 채널마다 다르고(`취소` `취소완료` `CANCEL` `반품접수`) 문구가 바뀝니다 |

### 결과

- 취소 문자열은 판매처에 붙습니다 (`channel_cancel_status`)
- `canceled_at` 이 찍힌 주문은 **출고·송장 액션이 잠깁니다.**
  취소된 걸 모르고 보내는 것이 이 시스템이 막으려는 사고입니다

## 2.17 낙관적 잠금을 쓰고 벌크는 부분 성공을 허용한다

## 2.18 실사는 기준 시각으로 비교한다

> [8-stock.md](../domain/8-stock.md) 2.1

### 배경

아침 9시에 세고 오후 2시에 확정하면 그 사이 출고분을 어떻게 처리할지가 문제입니다.

### 결정

실사 전표에 **기준 시각**(`base_at`)을 두고, 센 값과 **그 시각의 시스템 값**을
비교해 차이만 원장에 기록합니다. `moved_at` 도 기준 시각으로 적습니다.

```
9시   실물 20.  기준 시각 시스템 값 22
11시  3개 출고 → 원장 −3
14시  확정.    차이 20 − 22 = −2 를 원장에 (moved_at = 9시)

현재고 = 22 − 3 − 2 = 17   ✓
```

### 검토한 대안

| 대안 | 기각 사유 |
|---|---|
| 실사 중 입출고를 막는다 | 실사가 길어지면 그만큼 출고가 멈춰 고객 배송이 밀립니다 |
| 확정 시점 값을 덮어쓴다 | 세는 동안 나간 물건이 재고에 다시 살아납니다 |

### 결과

- **출고를 멈추지 않아도 됩니다.** 세는 동안의 이동은 이미 원장에 있습니다
- `moved_at` 을 확정 시각으로 적으면 "9시에 재고가 몇이었나"가 틀립니다
- `counted_quantity` 의 `NULL`(안 셌다)과 `0`(없다)을 구분합니다. 이 구분이 없으면
  안 센 것이 조용히 전량 손실로 조정됩니다

## 2.19 기부·폐기는 판매채널이 아니라 별도 도메인이다

> [9-disposal.md](../domain/9-disposal.md)

### 배경

유통기한이 임박한 상품을 단체에 기부하고 있고, 지난 것은 버립니다. 둘 다
**재고가 나가는데 매출이 없고 세무 증빙이 필요**합니다.

### 결정

**9번 도메인으로 둡니다.** 기부와 폐기를 한 전표에 구분값으로 담습니다.

새로 만드는 건 테이블 둘뿐입니다. 나머지는 값 하나씩만 추가했습니다 —
거래처에 `DONATION`, 원장에 `DISPOSAL`.

### 검토한 대안

| 대안 | 기각 사유 |
|---|---|
| 판매채널에 「기부」 판매처 추가 | 6번 주문은 채널 엑셀 import 전제로 설계됐습니다(`unique(channel_id, channel_order_no)` · `raw_data` · `import_batch` · 컬럼 소유권). 기부는 아무것도 안 씁니다. **"주문인데 주문이 아닌 것"** 이 생기고 모든 집계에 `단, 기부 채널 제외`가 붙습니다 |
| 8번 조정 사유에 「기부」 추가 | 재고는 맞지만 **누구에게 줬는지가 안 남습니다.** 조정은 숫자 바로잡기지 업무가 아닙니다 |
| 폐기는 안 적기 | 실사 차이에 "버렸다"와 "없어졌다"가 섞여 분실을 감지할 수 없습니다 |

### 결과

- 원장 구분값은 `DISPOSAL` **하나**입니다. 실사와 조정을 나눈 기준이
  **"근거 문서가 다른가"** 인데, 기부와 폐기는 같은 전표입니다
- 장부가는 **로트의 매입가**에서 자동으로 채우고 **컬럼에 저장**합니다.
  세무 자료로 나간 숫자가 조회할 때마다 달라지면 자료가 아닙니다
- 영수증은 나중에 오므로 `receipt_issued` 를 따로 둡니다.
  연말 명세에 **「영수증 미수령」 건수를 항상 같이** 보여줍니다
