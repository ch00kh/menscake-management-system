## 1.1 업무용어는 번역하지 않고 사전으로 지정한다

### 배경

업무용어의 원본은 한글이고 코드 식별자는 영문입니다. 그 사이를 사람이 그때그때
번역하면 **같은 것을 두 사람이 다르게 부릅니다.**

> "수주"를 누구는 `order`, 누구는 `sales_order`, 누구는 `receive_order`로 적으면 끝입니다.

### 결정

**용어사전에 1:1로 등록하고 등록된 값만 씁니다.** 번역이 아니라 지정입니다.

- 사전에 없는 업무용어는 **코드에 쓰기 전에 사전에 먼저** 추가합니다
- 축약하지 않습니다. 예외는 허용 목록뿐 — `id no url api db ui css html json csv`

### 검토한 대안

| 대안 | 기각 사유 |
|---|---|
| 각자 번역해서 쓰기 | 지금 상태. 같은 개념에 이름이 셋 |
| 영어 원어를 업무용어로 | 현장이 한글로 말합니다. 화면 문구까지 영어가 됩니다 |
| 사전 없이 네이밍 가이드만 | 가이드는 매번 판단을 요구합니다. 사전은 조회로 끝납니다 |

### 결과

- 코드 리뷰에서 이름 논쟁이 사라집니다. 사전에 있냐 없냐만 봅니다
- **사전이 코드를 못 따라가면 아무도 안 봅니다.** 그래서 "코드보다 먼저"가 규칙입니다
- 이 규칙을 정하면서 기존 코드도 폈습니다 — `qty` → `quantity`, `amt` → `amount`
- 사전 표기는 [ADR-004](ADR-004-스택-컨벤션.md) 4.3에서 `snake_case`로 확정됐습니다

## 1.2 시각은 UTC 저장, 금액은 문자열 전송, 코드값은 영문 저장

### 배경

날짜·금액·코드값은 모든 도메인에 나옵니다. 도메인마다 다르게 정하면 화면마다
다르게 보이고, 나중에 맞추는 건 데이터 마이그레이션입니다.

### 결정

| | 저장 | 전달·표시 |
|---|---|---|
| 시각 | `timestamptz` (UTC) | 화면에서 `Asia/Seoul` 변환 |
| 날짜만 | `date` | 그대로 |
| 금액 · 수량 | `numeric(18,2)` / `(18,3)` | **API로는 문자열** |
| 코드값 | 영문 `SCREAMING_SNAKE` | 한글 매핑 |

### 검토한 대안

| 대안 | 기각 사유 |
|---|---|
| KST로 저장 | 클라우드 서버 기본이 UTC라 한 곳만 어긋나면 9시간짜리 사고 |
| 날짜에도 타임존 | 자정 경계에서 날짜가 하루 밀립니다 |
| 금액을 JSON 숫자로 | JavaScript `number`가 정밀도를 잃습니다. 회계에서는 그대로 사고 |
| 코드값을 한글로 저장 | 인코딩 사고 · 가나다 정렬 · **표시명 변경이 데이터 변경이 됨** |

### 결과

- "진행"을 "처리중"으로 바꾸는 건 화면 문구 변경이지 마이그레이션이 아닙니다
- 계산은 서버가 합니다. 프런트는 문자열을 받아 표시 직전에만 포맷합니다

## 1.3 PK는 자동증가 정수, 업무번호와 분리한다

### 배경

ERP는 조인이 많습니다. 그리고 사용자가 보고 부르는 번호(`SO-2026-0841`)가
따로 있습니다. 이 둘을 섞으면 채번 규칙이 바뀔 때 PK를 건드리게 됩니다.

### 결정

```
id              bigint    자동증가. 내부 조인용. 화면에 노출하지 않는다
sales_order_no  varchar   업무번호. 사람이 부르는 이름
```

### 검토한 대안

| 대안 | 기각 사유 |
|---|---|
| UUID를 PK로 | 16바이트 랜덤이라 인덱스가 흩어집니다. 조인이 많은 ERP에 불리 |
| 업무번호를 PK로 | 연도 리셋·자릿수 변경이 **모든 FK를 건드리는 일**이 됩니다 |
| 복합 PK | 조인마다 컬럼이 늘고 FK 선언이 길어집니다 |

### 결과

- 전표 번호를 전부 연도별 리셋으로 갈 수 있었습니다 —
  `PO-` `RC-` `SH-` `ST-` `AJ-` `DP-`
- 분산 쓰기나 오프라인 생성이 필요해지면 그때 재검토합니다

## 1.4 감사 컬럼 5종, 삭제는 논리 삭제가 기본

### 배경

"누가 언제 만들고 고쳤나"는 감사에서 가장 먼저 나오는 질문입니다. 테이블마다
이름이 다르면 조회 로직을 테이블 수만큼 만들게 됩니다.

### 결정

```
created_at · created_by · updated_at · updated_by · deleted_at
```

**삭제는 논리 삭제가 기본**이고 조회는 `deleted_at is null`이 기본 조건입니다.

### 검토한 대안

| 대안 | 기각 사유 |
|---|---|
| 물리 삭제 기본 | ERP에서 전표를 지우면 감사 추적이 끊깁니다 |
| 모든 테이블에 짝 이력 테이블 | 테이블 수가 두 배가 됩니다 |
| `active boolean` 으로 통일 | 언제 지웠는지가 안 남습니다 |

### 결과

**예외가 둘 생겼고 둘 다 이유가 명시적입니다.**

| 예외 | 이유 |
|---|---|
| `partner_contact` — `deleted_at` 없음 | 개인정보. 물리 삭제해야 함 ([ADR-002](ADR-002-도메인.md) 2.13) |
| `stock_ledger` · `sales_order_history` · `access_log` — 수정·삭제 컬럼 없음 | append only. **컬럼이 아예 없어야 실수로 UPDATE 하는 코드가 안 나옵니다** |

## 1.5 레이아웃 번호는 사람과 에이전트의 지시 어휘다

### 배경

`frontend/src/layouts/`의 30종은 제품이 아니라 **부품**입니다. 그리고 작업 지시가
이렇게 나갑니다.

```
"상품 관리 만들어줘. 레이아웃 1번으로."
```

번호가 바뀌면 **과거 지시가 전부 틀어집니다.**

### 결정

`registry.ts`의 `no`는 PK와 같은 취급입니다.

- 재사용 금지 · 재배치 금지
- 레이아웃을 빼도 **번호는 결번으로** 남깁니다
- 이름은 바꿔도 되지만 번호가 가리키는 **화면 구조**는 바꾸지 않습니다

### 검토한 대안

| 대안 | 기각 사유 |
|---|---|
| 이름으로 지시 | "목록"이 여러 개입니다. 번호가 더 짧고 모호하지 않습니다 |
| 그룹 안에서 번호 매기기 | 그룹이 바뀌면 번호가 바뀝니다 |
| 필요할 때 재정렬 | 정확히 이걸 막는 게 이 결정의 목적입니다 |

### 결과

- `/gallery`는 개발용 참고물이 아니라 **지시할 때 계속 보는 화면**입니다
- 도메인 문서 9개가 화면마다 레이아웃 번호를 박아뒀습니다

## 1.6 브랜치가 배포 환경이다

### 배경

서버가 개발·운영 둘입니다. 어디에 무엇이 올라가 있는지를 사람이 기억하면
반드시 틀립니다.

### 결정

```
main   운영 서버   ← dev (릴리스), hotfix/*
 ↑
dev    개발 서버   ← feature/*, fix/*
```

**핫픽스는 `main`에서 따서 `main`에 넣고, 즉시 `main`을 `dev`로 역병합합니다.**

### 검토한 대안

| 대안 | 기각 사유 |
|---|---|
| 태그로 배포 | 지금 무엇이 어디 있는지 브랜치만 봐서는 모릅니다 |
| trunk 기반 + 피처 플래그 | 5명 팀에 플래그 관리 비용이 과합니다 |
| git-flow 전체 | release 브랜치까지는 필요 없습니다 |

### 결과

- 브랜치 이름이 곧 "지금 어디에 있나"입니다
- **역병합을 빼먹으면 다음 릴리스가 핫픽스를 되돌립니다.** 규칙에 명시했습니다

## 1.7 시스템 테마는 팔레트 축과 명암 축을 분리한다

> TODO 단계 밖입니다. 백엔드와 무관하게 진행한 작업입니다.

### 배경

기본 흑백 테마를 송편에서 딴 색으로 바꾸기로 했습니다. 후보를 비교했는데 초기 안
두 개가 **사실상 구분되지 않았습니다** (primary 가 `0.45 0.055 148` vs
`0.44 0.06 148`). 아트보드 내용까지 서로 달라 비교가 흐려진 것도 원인이었습니다.

### 결정

```
팔레트 축   쑥(기본) · 치자 · 백년초     사용자가 고른다
명암 축     light · dark · system       사용자가 고른다
```

- 다크는 **솔잎 지반을 공유**하고 팔레트는 `--primary` 계열만 바꿉니다
- 저장은 지금 `localStorage`, 로그인 후에는 DB가 진실
  (`account.theme_palette` · `account.theme_mode`)
- 첫 페인트 깜빡임은 `<head>` 인라인 스크립트로 막습니다

### 검토한 대안

| 대안 | 기각 사유 |
|---|---|
| 색과 명암을 한 테마로 | 조합이 6개가 되고 토큰을 6벌 관리하게 됩니다 |
| 다크에서도 팔레트별 지반 분리 | 유지할 토큰이 두 배인데 눈에 띄는 차이가 적었습니다 |
| 한 컬럼에 `"sugg-dark"` 로 저장 | 축이 섞여 파싱이 필요해집니다. **컬럼 둘로 둡니다** |

### 결과

- 팔레트를 추가하려면 `--primary` 계열만 정의하면 됩니다
- **후보 비교는 한 템플릿에서 색만 바꿔 생성해야 한다**는 걸 배웠습니다.
  내용이 다르면 색 차이를 못 봅니다
