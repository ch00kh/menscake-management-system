## 3.1 규모가 작다 — 단일 DB로 충분하다

### 입력값

| 항목 | 값 |
|---|---|
| 일 주문 | 100~500건 |
| SKU | 500~3,000개 |
| 판매처 | 1~3개 |
| 동시 접속 | 1~2명, 피크 3명 (추정) |

상한(500건 · 3,000 SKU)으로 계산했습니다. 하한으로 잡으면 스택을 고르고 나서
모자랍니다.

### 결론

**5년 누적 약 870만 행 / 4.5 GB.**

| 안 씀 | 왜 |
|---|---|
| 샤딩 · 파티셔닝 | 단일 인스턴스로 여유 |
| Redis · 캐시 계층 | 동시 3명. 캐시가 해결할 경합이 없음 |
| 검색 엔진 | 인덱스 + `LIKE` 로 충분 |
| Spring Batch · 잡 큐 | 배치가 하루 4건 |
| Kubernetes | 서버 한 대 |
| GraphQL | 클라이언트 하나, 조회가 정해져 있음 |
| 가상 스크롤 | 화면당 최대 6,000행 |

| 씀 | 왜 |
|---|---|
| 서버 페이징 | 주문이 5년 91만 행 |
| 트랜잭션 | 확정 한 번이 테이블 4~5개를 바꿈 |
| 서버 엑셀 파싱 | 위저드가 커밋 전에 전체를 검증 |
| 크론 | 개인정보 파기 2건 + 안전재고 + 접속기록 정리 |

### 발견

**`raw_data` 가 용량의 절반입니다.** `sales_order` 행이 1.5 KB인 건 이것 때문이고
나머지 컬럼을 다 합쳐도 500 B가 안 됩니다. 용량이 문제가 되면 여기가 첫 번째로
손볼 곳이고, 오래된 주문의 `raw_data` 만 비우면 됩니다 — 파생 데이터입니다.

### 재검토 트리거

```
일 주문 2,000건 초과 · DB 20 GB 초과 · SKU 10,000 초과
동시 접속 10명 초과 · 판매처 9개 초과
```

### 정직하게 남긴 것

주문당 라인 수 1.5, 주문당 이력 행 5는 **추정이지 관측값이 아닙니다.**
첫 import 후 실측으로 교체합니다.

## 3.2 백엔드는 Java + Spring Boot. Supabase 기각

### 배경

이전 초안이 Supabase(Postgres + Auth + RLS)를 확정으로 잡았고, 도메인 설계 때
"3단계의 출발점"으로 판정해뒀습니다. **출발점으로 쓰되 채택하지는 않았습니다.**

### 결정

**Java 21 + Spring Boot 3.** 팀 선택입니다.

### 검토한 대안

| 대안 | 기각 사유 |
|---|---|
| Supabase 유지 | **범위가 달라졌습니다.** 초안의 v1은 주문 취합 하나였는데 지금은 도메인 9개고 그 사이에 트랜잭션 로직이 생겼습니다 (아래) |
| TypeScript 백엔드 | 프런트와 언어가 통일되고 타입 공유가 되지만, **팀이 이미 잘 쓰는 게 더 중요합니다** |
| Python / FastAPI | 같은 이유 |

**Supabase 를 기각한 구체적 근거 둘**

1. 확정 로직이 무겁습니다 — 입고 확정(원장+현재고+발주라인+발주상태),
   출고 확정(원장 세트전개+현재고+주문상태), 재import(컬럼 소유권+취소 감지+
   이력 화이트리스트+파기 예외), 실사 확정. 클라이언트에서 하면 안 되고
   Postgres 함수나 Edge Function 으로 밀면 **백엔드만큼의 코드를 테스트하기
   불편한 환경에서** 쓰게 됩니다
2. **RLS 가 벌어줄 게 별로 없습니다.** 우리 권한 모델은 `(역할, 메뉴, 행위)` —
   엔드포인트 단위 인가입니다. 팀 전원이 모든 주문을 보므로 행 단위 필터링이
   거의 없습니다

### 초안에서 살린 것

| | |
|---|---|
| Postgres | 그대로 |
| 이력 화이트리스트 | 그대로 |
| 디스코드 Webhook | 그대로. 호출 위치만 Edge Function → 서버 |
| 트리거로 이력 남기기 | **애플리케이션으로 옮김** — `changed_by` 와 `source`(import/수동)를 트리거가 모릅니다 |
| 엑셀 파싱 | SheetJS → **Apache POI** (서버로 옮겨서). 배포 채널 우려도 같이 해소 |
| vitest | 프런트 그대로. 백엔드는 JUnit 5 |

### 따라온 선택

`Flyway` · `JPA + QueryDSL` · `Apache POI` · `@Scheduled`(Spring Batch 아님) ·
`Gradle` · `docker compose 는 Postgres만`.

## 3.3 DB는 PostgreSQL

### 배경

설계에서 걸리는 게 셋 있었습니다 — 부분 유니크 인덱스 3건, 채널 원본을 담는 JSON
컬럼, UTC 저장 + KST 표시.

### 결정

**PostgreSQL.** 설계를 그대로 옮길 수 있습니다.

### 검토한 대안

| 대안 | 기각 사유 |
|---|---|
| MySQL / MariaDB | 부분 유니크가 없어 생성 컬럼으로 우회해야 하고(3건), 타임존을 애플리케이션이 더 밀접하게 다뤄야 합니다 |

### 결과

- `create unique index ... where` 를 그대로 씁니다
- `jsonb` · `timestamptz` 를 그대로 씁니다
- **테스트에 H2 를 쓸 수 없게 됐습니다** ([ADR-004](ADR-004-스택-컨벤션.md) 6장)

## 3.4 인증은 세션 쿠키. JWT 기각

### 배경

**설계가 정해줬습니다.** 1단계에서 퇴사 처리를 `active = false` 로 정했습니다.

### 결정

**세션 쿠키 + Spring Session JDBC.** 비밀번호는 BCrypt.

### 검토한 대안

| 대안 | 기각 사유 |
|---|---|
| JWT | 토큰이 만료될 때까지 유효합니다. **계정을 막아도 즉시 안 끊깁니다.** 게다가 브라우저 전용 사내 도구라 JWT 가 벌어주는 것(모바일 앱·크로스 도메인)이 없습니다 |
| 인메모리 세션 | 서버가 한 대라 되지만 재배포마다 전원 로그아웃됩니다 |

### 결과

- 퇴사자 계정이 **다음 요청에서 바로** 막힙니다
- 로그인할 때 유효 권한 집합을 세션에 적재하고
  `@RequirePermission` 이 검사합니다 ([ADR-004](ADR-004-스택-컨벤션.md) 1장)

## 3.5 사내 서버 2대 — 관리형 DB를 포기한 대가

### 배경

규모는 작습니다 — 5년 4.5 GB, 동시 3명. 서버 한 대로 충분합니다. 다만
**수령인 정보와 거래처 담당자 연락처**를 다룹니다.

### 결정

**사내 서버 2대** (개발 · 운영). 팀 선택입니다.

```
nginx        TLS 종료 · 정적 파일(프런트 빌드) · /api 리버스 프록시
spring-boot  애플리케이션
postgres     DB (볼륨)
```

### 검토한 대안

| 대안 | 기각 사유 |
|---|---|
| 클라우드 + 관리형 DB | 자동 백업·시점복구를 그대로 받지만, 팀이 사내 인프라를 택했습니다 |

### 결과 — **자동으로 되지 않는 것들이 생겼습니다**

백업 · 복구 리허설 · 접근 통제 · 보안 패치 · 로그 보관이 전부 팀 책임이 됐습니다.
그래서 3.6~3.8을 따로 정했습니다.

프런트를 Spring Boot static 이 아니라 nginx 가 서빙합니다 — SPA fallback 과 TLS 를
한곳에서 처리하고, 프런트만 다시 배포할 수 있습니다.

## 3.6 백업은 하루 1회 사내 NAS, 복구 리허설은 분기 1회

### 결정

| | |
|---|---|
| 주기 | 하루 1회, 새벽 (주문 업로드 전) |
| 보관 | 일 7 · 주 4 · 월 6 세대. 압축하면 10 GB 미만 |
| 암호화 | **필수.** 파일 자체를 암호화한 뒤 옮김 |
| 위치 | **사내 NAS** |
| 리허설 | **분기 1회.** 개발 서버에 복원 |

### 하루치를 잃으면 무엇을 잃나 — 주기의 근거

| 잃는 것 | 복구 |
|---|---|
| 주문 · 주문라인 | **채널에서 다시 import 하면 돌아옵니다** |
| 상태 · 담당자 · 메모 | **못 살립니다.** 운영 소유 컬럼 |
| 전표 | 못 살립니다 |

**진짜 잃는 건 "운영 상태"** — 이 시스템이 존재하는 이유 그 자체입니다.
시점 복구(WAL 아카이빙)가 필요해지면 그때 붙입니다.

### 검토한 대안

| 대안 | 기각 사유 |
|---|---|
| 서버 안에만 백업 | 디스크 고장·러섬웨어에 아무 도움이 안 됩니다 |
| 클라우드 오브젝트 스토리지 | 팀이 사내 보관을 택했습니다 |

### 남은 위험 — 기록만 하고 다시 따지지 않습니다

건물 단위 사고(화재·침수)에는 서버와 NAS가 **같이 당합니다.** 알고 고른 것입니다.
값싼 보완책 하나는 적어뒀습니다 — **월 1회 세대 하나를 사외로.**

### 리허설이 만드는 위험

**복원하는 순간 개발 서버에 운영 개인정보가 들어갑니다.** 개발 서버는 보통
접근이 헐겁습니다. 그래서 복원 직후 **익명화가 필수**이고, 익명화 스크립트를
백업 스크립트와 **같이 관리**합니다 — 따로 두면 언젠가 안 돌립니다.

## 3.7 DB 계정을 셋으로 나눈다

### 결정

| 계정 | 권한 | 쓰는 곳 |
|---|---|---|
| `app` | 테이블 읽기·쓰기. **DDL 없음** | 애플리케이션 |
| `migrator` | DDL 포함 | Flyway 실행 시에만 |
| `ops_*` | 읽기 전용. **사람마다 하나씩** | 운영자 임시 조회 |

서버는 SSH 키 전용, 5432는 앱 서버에서만, nginx TLS 필수.

### 검토한 대안

| 대안 | 기각 사유 |
|---|---|
| 계정 하나 | 애플리케이션 취약점이 스키마까지 갑니다 |
| 공용 운영 계정 | 누가 운영 DB를 직접 봤는지가 안 남습니다 |
| "사내망이니까 괜찮다" | 개인정보 DB에 사무실 어느 자리에서나 붙을 수 있으면 통제가 아닙니다 |

### 결과

이 분리가 3.8에서 한 번 더 쓰입니다.

## 3.8 개인정보 접속기록을 화면·API 단위로 남긴다

### 배경

지금까지 설계한 이력(`sales_order_history`)은 **바꾼 것**만 남기고 **본 것**은
안 남깁니다. 개인정보를 다루는 시스템은 누가 언제 접근했는지를 일정 기간
보관하게 되어 있습니다.

> 일반적으로 통용되는 기준이지 법률 자문이 아닙니다. 최종 확인은 따로 받습니다.

### 결정

`access_log` 테이블을 둡니다. **화면·API 단위**로 남깁니다.

| 상황 | 남는 것 |
|---|---|
| 주문 목록을 염 | 엔드포인트 · 필터 조건 · 결과 42건 |
| 주문 한 건을 염 | 위 + `target_type = ORDER` · `target_id = 12345` |

- 보관 **2년** (설정값). 크론이 만료분을 지웁니다
- **`app` 계정에 `DELETE` · `UPDATE` 권한을 주지 않습니다.** `purger` 계정만 지웁니다

### 검토한 대안

| 대안 | 기각 사유 |
|---|---|
| 모든 조회를 행 단위로 | 목록 한 번 열 때마다 수십 행이 쌓여 **접속기록이 주문 테이블보다 커집니다** |
| 로그인·로그아웃만 | 유출 의심이 생겼을 때 누가 뭘 봤는지 답할 수 없습니다 |

### 결과

- 목록에서 뭘 봤는지는 **조회 조건 + 건수**로 재현됩니다
- **조회된 값 자체는 안 남깁니다.** 담으면 그게 또 하나의 개인정보 사본이 되고
  파기할 곳이 하나 더 늘어납니다 — 파기 로그와 같은 원칙입니다
- 5명 × 하루 100회 × 2년 ≈ 36만 행. 주문 테이블의 절반도 안 됩니다
- 애플리케이션 코드가 아무리 잘못돼도 접속기록을 지울 수 없어야 기록에 의미가 있습니다
