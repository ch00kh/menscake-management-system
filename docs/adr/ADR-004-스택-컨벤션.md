## 4.1 컨트롤러와 서비스 사이에 유스케이스를 둔다

### 배경

DDD와 클린 아키텍처를 따르되 가볍게 가기로 했습니다. 그리고 우리 설계에서
**확정 한 번이 테이블 4~5개를 바꿉니다.**

```
출고 확정   원장(세트 전개) + 현재고 + 주문 상태 + 전표
입고 확정   원장 + 현재고 + 발주라인 + 발주 상태
재import    주문 + 라인 + 이력 + 배치 + 취소 감지
```

### 결정

```
com.n2soft.erp
├─ common/          audit · error · page · security
└─ salesorder/                   ← 도메인 하나. 문서 9개와 1:1
    ├─ api/         Controller + Request/Response
    ├─ usecase/     쓰기. 트랜잭션 경계
    ├─ query/       읽기 전용. QueryDSL
    ├─ domain/      엔티티 · 도메인 서비스 · Repository 인터페이스
    └─ infra/       JPA Repository 구현
```

- **`domain` 은 다른 층을 모릅니다.** Repository **인터페이스**가 `domain` 에,
  구현이 `infra` 에. 클린 아키텍처에서 **이 의존성 역전 하나만** 지킵니다
- **유스케이스 하나 = 동사 하나.** public 메서드는 `execute` 하나
- **`@Transactional` 은 유스케이스에만**

### 검토한 대안

| 대안 | 기각 사유 |
|---|---|
| 계층별 패키지 (controller/service/…) | 기능 하나 고치려면 폴더 네다섯 곳을 오갑니다 |
| 도메인별 + 내부 계층 없이 평평하게 | 입고·주문처럼 파일이 20개 넘는 도메인이 금방 답답해집니다 |
| 유스케이스 없이 서비스만 | 서비스가 비대해지고 **트랜잭션 경계가 어디인지 흐려집니다** |
| 순수 도메인 객체와 JPA 엔티티 분리 | 정석이지만 매핑 클래스가 두 배. **5명이 쓰는 시스템에는 과합니다** |

### 결과

- 유스케이스 이름이 곧 트랜잭션 경계입니다 — `ConfirmShipmentUseCase`,
  `ImportSalesOrdersUseCase`, `PurgeReceiverInfoUseCase`
- **타협을 문서에 적어뒀습니다** — 엔티티에 JPA 애노테이션을 붙입니다.
  바꿀 시점은 도메인 로직이 JPA 때문에 뒤틀리기 시작할 때입니다
- 도메인 간에는 상대의 `domain` 공개 인터페이스만 부릅니다. 순환 참조 금지

## 4.2 읽기는 유스케이스를 거치지 않는다

### 결정

```
쓰기   api → usecase → domain/infra     트랜잭션 있음
읽기   api → query                       읽기 전용
```

`query` 는 QueryDSL로 DTO를 바로 만들어 돌려줍니다. **엔티티를 반환하지 않습니다.**

### 검토한 대안

| 대안 | 기각 사유 |
|---|---|
| 조회도 유스케이스로 | 껍데기 클래스만 늘어납니다 |
| 리포지토리가 엔티티를 그대로 반환 | 지연 로딩이 컨트롤러까지 새어 나가면 **N+1이 화면에서 터집니다** |

## 4.3 식별자 정본은 snake_case, 예약어는 개명한다

### 배경

논리명은 camelCase였는데, DB 관례는 소문자 snake_case입니다. 그리고
**`user` 와 `order` 가 Postgres 예약어**라 따옴표 없이 못 씁니다.

### 결정

**용어사전의 `snake_case` 가 정본입니다.** Java 필드와 TypeScript 속성은 이걸
camelCase로 바꾼 것이고, 변환이 기계적이라 사전에 따로 적지 않습니다.

```
sales_order_no  ↔  salesOrderNo
```

예약어 둘은 **이름 자체를 바꿨습니다.**

```
사용자   user   →  account
주문     order  →  sales_order
```

### 검토한 대안

| 대안 | 기각 사유 |
|---|---|
| 따옴표로 감싸기 | 수동 쿼리를 쓸 때마다 불편합니다 |
| `tb_` 접두사 | 모든 테이블명에 정보 없는 접두사가 붙습니다 |
| 전부 복수형 | 규칙이 하나가 되지만 `receivings` `stocks` 처럼 어색한 이름이 생깁니다 |
| 물리명만 바꾸고 논리명은 유지 | 한 대상에 이름이 둘이 됩니다. **[ADR-001](ADR-001-기반.md) 1.1이 금지하는 것** |

### 결과

- **회피가 아니라 개명이므로 규칙의 예외가 아닙니다**
- 덤이 하나 — `purchase_order`(발주)와 `sales_order`(주문)가 대칭이 되어
  매입/판매가 이름에서 바로 읽힙니다
- 설계 문서 14개와 용어사전을 전부 바꿨습니다
- 인덱스 명명은 `pk_` `fk_` `ux_` `ix_` `ck_` 접두. 테이블과 컬럼 사이는
  밑줄 **둘** — 컬럼명 자체에 밑줄이 있어 하나로는 경계가 안 보입니다

### 부산물 — 부분 유니크 인덱스 3건

Postgres 는 `create unique index ... where` 를 지원합니다. 다만 하나가
그대로는 안 됐습니다.

| 대상 | 방식 |
|---|---|
| `stock` | `lot_id` NULL 여부로 인덱스 **둘**. NULL은 서로 다른 값으로 취급되므로 하나로는 못 막습니다 |
| `stocktaking_line` | 같은 모양 |
| `shipment_sales_order` | **`canceled boolean` 컬럼을 새로 뒀습니다** |

마지막 건이 문제였습니다 — "취소되지 않은 출고에 한해 주문은 하나"인데
`status` 는 `shipment` 에 있고 **부분 인덱스는 다른 테이블을 참조할 수 없습니다.**
그래서 그 조건을 `shipment_sales_order` 로 가져왔습니다. 의도적 중복입니다.

애플리케이션 검사만으로는 **두 사람이 동시에 누르면 뚫립니다.**

## 4.4 API는 순수 REST + RFC 7807, 공통 래퍼 없음

### 배경

프런트 타입을 OpenAPI에서 자동 생성하기로 했으므로, 이 선택이 **생성된 타입 모양에
그대로 나타납니다.**

### 결정

- 성공은 **데이터를 그대로**. 목록은 페이지 객체
- 실패는 HTTP 상태 + `application/problem+json` (RFC 7807) + 확장 필드 `code`
- URL은 kebab-case 복수형 — `/api/sales-orders`

| 상태 | 언제 |
|---|---|
| 400 | 형식 · 필수값 |
| 401 / 403 | 미인증 / 권한 없음 |
| 404 | 대상 없음 |
| **409** | 낙관적 잠금 충돌 · 유니크 위반 |
| **422** | 업무 규칙 위반 |

### 검토한 대안

| 대안 | 기각 사유 |
|---|---|
| 공통 래퍼 `{data, error}` | 생성된 타입을 매번 벗겨내는 코드가 생깁니다 |
| 공통 래퍼 + 항상 200 | nginx 로그·모니터링·브라우저 도구가 전부 「정상」으로 보여 **장애를 늦게 압니다** |
| 409와 422를 하나로 | 프런트가 다르게 반응해야 합니다. 409는 "다시 불러와 재시도", 422는 "다시 해도 안 됨" |

### 결과

- `code` 로 분기합니다. 문구로 분기하면 문구를 못 바꿉니다
- **벌크는 200 + 부분 성공 배열**입니다 — 전체가 실패한 게 아니기 때문입니다
  ([ADR-002](ADR-002-도메인.md) 2.17)
- 페이지네이션은 offset 기반, `size` 상한 200. 실무 조회가 최근 30일이라 깊은
  페이지가 없습니다
- 금액은 문자열, 없는 값은 필드를 생략하지 않고 `null` 명시 —
  생략하면 생성 타입이 전부 옵셔널이 되어 쓸모없어집니다

## 4.5 코드값은 Postgres enum 대신 varchar + CHECK

### 배경

**값이 실제로 늘었습니다.** `source_type` 은 설계 도중 셋에서 넷, 다섯이 됐습니다
(`RECEIVING` `SHIPPING` → `+STOCKTAKING` `+ADJUSTMENT` → `+DISPOSAL`).

### 결정

```sql
source_type varchar(20) not null
  constraint ck_stock_ledger__source_type
  check (source_type in ('RECEIVING','SHIPPING','STOCKTAKING','ADJUSTMENT','DISPOSAL'))
```

### 검토한 대안

| 대안 | 기각 사유 |
|---|---|
| Postgres `create type ... as enum` | `ALTER TYPE ... ADD VALUE` 는 제약이 많고 **값을 지울 수 없습니다** |
| 코드 테이블(FK) | 값이 코드 로직과 묶여 있어 DB에서 관리할 이유가 없습니다 |

### 결과

- 제약을 바꿔 다시 걸면 끝입니다
- JPA `@Enumerated(EnumType.STRING)` 과 그대로 맞습니다

## 4.6 마이그레이션은 앞으로만 간다

### 결정

```
V{yyyyMMddHHmm}__{snake_case_설명}.sql
V202609041530__create_account_and_role.sql
```

- **타임스탬프 버전.** 두 사람이 같은 날 만들어도 겹치지 않습니다
- **롤백 없음.** Flyway Community 에 undo 가 없습니다
- 파괴적 변경은 **두 릴리스로** — (1) 새 컬럼 추가 + 양쪽 쓰기 + 백필,
  (2) 다음 릴리스에서 옛 컬럼 DROP
- **적용된 파일 수정 금지.** 체크섬이 깨져 다음 배포가 멈춥니다
- `migrator` 계정으로만 실행. 시드(ADMIN 역할·초기 관리자·기본창고·메뉴 트리)도
  마이그레이션입니다

### 검토한 대안

| 대안 | 기각 사유 |
|---|---|
| 순번 버전 (`V1` `V2`) | 반드시 충돌합니다 |
| Liquibase | XML 추상화가 우리 규모에서 얻는 게 없고, **DB 고유 기능을 그대로 써야** 합니다(부분 유니크 3건) |
| 한 번에 파괴적 변경 | 롤백할 방법이 없습니다 |

## 4.7 통합 테스트는 Testcontainers로 — H2 금지

### 배경

우리 로직의 핵심이 전부 **DB 트랜잭션 안에** 있습니다.

### 결정

| | 대상 | DB |
|---|---|---|
| 단위 | 도메인 로직 · 계산 | 없음 |
| 통합 | 유스케이스 | **Testcontainers Postgres** |

컨테이너 재사용을 켭니다. 테스트도 **같은 Flyway 마이그레이션을 태웁니다** —
별도 스키마 스크립트를 만들면 마이그레이션 자체가 검증되지 않습니다.

### 검토한 대안

| 대안 | 기각 사유 |
|---|---|
| H2 인메모리 | 부분 유니크 · `jsonb` · `timestamptz` · `CHECK` 가 전부 Postgres 고유입니다. **H2에서 통과한 테스트는 아무것도 증명하지 못합니다** |
| 공용 개발 DB | 테스트가 서로를 밟습니다 |

### 결과 — 반드시 있어야 하는 회귀 테스트 9건

**여기가 틀리면 조용히 틀립니다.** 화면에는 아무 일도 없어 보입니다.

| # | 무엇 |
|---|---|
| 1 | 취소 감지는 `canceled_at IS NULL` 일 때만 발화 — 재import 2회에 값이 안 바뀜 |
| 2 | 재import 가 `status` · `assignee_id` · `memo` 를 보존 |
| 3 | `receiver_purged_at` 이 있으면 수령인을 덮어쓰지 않음 |
| 4 | 벌크 20건 중 3건 stale → 17건 반영 + 3건 실패 목록 |
| 5 | 실사 중 출고가 있어도 기준 시각 차이 계산이 맞음 |
| 6 | 세트 출고가 구성품으로 전개돼 차감됨 |
| 7 | 부분 유니크 3건이 실제로 막음 |
| 8 | 발주 상태가 `ORDERED → PARTIAL → COMPLETED` 로 자동 전이 |
| 9 | `ADMIN` 활성 사용자를 0명으로 만들 수 없음 |

프런트는 vitest 입니다. 현재 0건입니다.

## 부록 — 린트 · 포맷

| | |
|---|---|
| Java | Spotless + google-java-format **(AOSP, 4칸)** |
| 줄 길이 | 120 |
| 프런트 | 기존 ESLint + Prettier 유지 |

AOSP 변형을 쓰는 이유는 기본 2칸이 국내 관례와 멀고, 한글 주석이 섞이면 들여쓰기가
눈에 안 들어오기 때문입니다.

**검사는 빌드에서 합니다.** pre-commit 훅은 두지 않습니다 — 우회가 쉽고
**진실은 CI에 있어야** 합니다.
