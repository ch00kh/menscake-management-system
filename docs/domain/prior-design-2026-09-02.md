# (보관) 쇼핑몰 운영팀 공유 상태 계층 — 살린 부분

## 1. 문제 정의

5명 이상이 교대·야간 근무로 돌아가는 쇼핑몰 운영팀이, 구글 공유 스프레드시트와 디스코드로
주문·재고를 관리하고 있다. 시트는 데이터를 담고 디스코드는 그 데이터의 **상태**를 담는다 —
"이거 처리했어요?" "네"가 현재의 워크플로 엔진이자 감사 로그다.

교대가 바뀌면 다음 사람은 디스코드 스크롤백을 읽어야 지금 뭘 해야 하는지 알 수 있다.
빈 셀이 "아직 안 함"인지 "누가 했는데 안 적었음"인지 구분되지 않는다.

만들려는 것은 ERP UI가 아니라 **주문 행의 상태 + 담당자 + 시각**을 권위 있게 보유하고,
교대 경계를 넘어 살아남는 공유 운영 상태 계층이다.

**설계 리트머스**: *디스코드 스크롤백 없이, 처음 보는 야간 담당자가 화면만 보고 지금 뭘
해야 하는지 정확히 아는가?* 모든 결정을 이 문장에 대본다.

> 이 장은 [scope.md](scope.md) 1장이 그대로 가져갔습니다.

## 2. 수요 근거

- 현재 시스템: 구글 공유 스프레드시트 + 디스코드 (원문: "현재는 직원들끼리 구글 공유
  스프레드시트와 디스코드로 **소통**하고 있어")
- 사용자 규모: 5명 이상, 교대·야간 포함
- 명시적 요청 3건: ① 주문 취합→출고 ② 재고 수량 맞추기 ③ 거래처 저장
- 통증 유형: 반복 수작업으로 시간 소모

**증거 강도 (솔직히)**: 중간. 관찰된 행동(시트+디스코드 운용, 교대 편성)은 실재하지만
"몇 시간을 쓰는가", "지난달에 이것 때문에 무슨 사고가 났는가"라는 숫자가 없다.

> 초안은 그 숫자를 얻는 관찰 과제를 두었으나 **채택되지 않았습니다.**

## 5. 시장 분석에서 나온 통찰

업계 글은 스프레드시트의 **단점**만 나열한다. 대체 실패의 원인은 대체품이 스프레드시트의
**장점**(붙여넣기·키보드 속도·동시 편집)을 못 따라가서다. ERP 도입 실패를 "직원 저항"이라
부르지만 실제로는 **입력 속도 퇴행**이다.

→ **이 팀의 정답은 "더 빠른 입력"이 아니라 "입력 제거(import)"다.**

## 7. 살린 설계 규칙 — 재import · 취소 감지 · 낙관적 잠금

**초안에서 가장 밀도가 높은 부분이고 그대로 6번 도메인이 됐다.** 아래는 원문이며,
컬럼명은 초안 당시 이름이다(현행은 [6-order.md](6-order.md)).

**재import UPSERT 컬럼 소유권** (리뷰어 지적: 이게 없으면 구현 착수 불가)

| 소유 | 컬럼 | 재import 시 |
|---|---|---|
| 채널 소유 | `channel_status, ordered_at, buyer_*, ship_address, raw`, `order_items` 전체 | **덮어씀** |
| 운영 소유 | `status, assignee, memo, waybill_no` | **보존** (덮어쓰지 않음) |
| 파생 | `canceled_at` | 아래 규칙으로 **세팅**, 한 번 세팅되면 되돌리지 않음 |

**취소 감지 규칙** (성공기준 4와 그 회귀 테스트가 이 두 줄에 걸려 있다)

1. `channel_status`가 채널별 취소 문자열 집합에 포함되면 `canceled_at = now()`.
   채널마다 문자열이 다르므로(취소/취소완료/CANCEL/반품접수…) 하드코딩하지 않고 매핑에 둔다.
2. **직전 배치에 있었으나 이번 배치에 없는 행**: 자동 취소 처리하지 **않는다**(export 기간
   필터 때문일 수 있음). 대신 "이번에 안 보인 행 N건"을 남기고 작업 큐에 `확인필요` 배지만
   띄운다.

`canceled_at IS NOT NULL`인 행은 작업 큐에서 **취소 경고 배지 + 출고/송장 액션 비활성화**.

**낙관적 잠금과 벌크 처리**

- UPDATE는 `where id = ? and version = ?` 조건부.
- 단건 충돌: "다른 사람이 방금 바꿨습니다" 배너 + 최신값 diff 표시 + 재시도.
- **벌크(20행 일괄 상태변경 중 3행 stale)**: 전체 롤백하지 않는다. **부분 성공 + 실패한 행
  목록 반환 + 그 행만 재시도** 버튼. 핵심 기능이 벌크이므로 전체 롤백은 쓸 수 없다.

> 현행: [ADR-002](../adr/ADR-002-도메인.md) 2.15 · 2.16 · 2.17.
> 이 규칙들은 [convention-stack.md](../convention-stack.md) 6.2의 필수 회귀 테스트
> 1~4번이 됐습니다.

## 8. 성공 기준

1. **교대 인계에서 디스코드 스크롤백을 읽지 않는다.** (측정: 인계 시점 디스코드 메시지 수,
   도입 전후 1주씩)
2. **주문 마감 시간이 줄어든다.** 늘어나면 즉시 실패. (측정: 도입 전 1주 / 후 1주)
3. **주문 시트에 대한 이중 입력이 없다.** 배포 후 4주 안에 주문 시트가 read-only가 되거나
   폐기. (시계는 배포일에 시작한다)
4. **취소된 주문이 출고 지시로 뜨지 않는다.** 한 번이라도 나면 신뢰가 죽는다.
   회귀 테스트로 고정한다.

> 4번의 회귀 테스트가 [convention-stack.md](../convention-stack.md) 6.2의 1번입니다.

## 9. 화면 재사용에 대한 정정 — 5단계 구현 때 유효

리뷰어가 파일을 열어 확인한 결과, 최초 문서의 "재사용" 표기는 과장이었다. 정정한다.

| 화면 | 기반 레이아웃 | 실제로 재사용되는 것 | 신규로 써야 하는 것 |
|---|---|---|---|
| Import 3단계 | `form-wizard(16)` | 스텝퍼 UI, 카드 셸 | 파일 드롭, 컬럼 매핑 UI, 검증, 행별 판정 표, 커밋 |
| 작업 큐 | **`approval-inbox(24)`** | 좌 목록 + 우 상세 + 액션 버튼 셸 | 선택 UI **전무**(24는 `<button>` 리스트에 체크박스·페이지네이션이 아예 없다) → 다중선택·벌크 상태/담당·인라인 편집·실제 페이지네이션 전부 신규 |
| 행별 이력 팝오버 | `record-timeline(10)` | 타임라인 `<ol>` 약 28줄만 발췌 | Popover 래핑, 이력 바인딩, batch 묶기 |
| 상태 진행 표시 | `workflow-status(25)` | 스텝퍼 마크업 | 상태 상수 바인딩 |

**핵심 정정**: 재사용은 **셸과 시각 언어 수준**이고 로직은 전부 신규다. 최초 문서가 이 표로
일정을 정당화한 것이 가장 큰 오류였다.

`src/components/erp/record-table.tsx`의 `RecordTable`은 `data`/`columns`/`onRowClick`
props를 받지만 **체크박스가 비제어이고 `TableFooterBar`의 페이지네이션은 `href="#"`
리터럴이다.** 작업 큐에서는 이 컴포넌트를 쓰지 않고 새로 만든다.

**"교체"의 범위** — 작업 큐에서 쓰지 않는다는 뜻이지 리포지토리에서 제거한다는 뜻이 아니다.
`RecordTable`을 import하는 레이아웃이 13개이고 갤러리는 `/gallery`로 계속 살려 두므로
**기존 컴포넌트는 그대로 둔다.**
