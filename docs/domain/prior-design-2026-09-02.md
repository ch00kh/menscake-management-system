# Design: 쇼핑몰 운영팀 공유 상태 계층 (ERP v1)

Generated by /office-hours on 2026-09-02
Branch: master
Repo: shadcn-skill-test (로컬, 원격 없음 — Dependencies 참조)
Status: DRAFT (adversarial review 3회 반영)
Mode: Startup (intrapreneurship — 사내 도구)

## Problem Statement

5명 이상이 교대·야간 근무로 돌아가는 쇼핑몰 운영팀이, 구글 공유 스프레드시트와 디스코드로
주문·재고를 관리하고 있다. 시트는 데이터를 담고 디스코드는 그 데이터의 **상태**를 담는다 —
"이거 처리했어요?" "네"가 현재의 워크플로 엔진이자 감사 로그다.

교대가 바뀌면 다음 사람은 디스코드 스크롤백을 읽어야 지금 뭘 해야 하는지 알 수 있다.
빈 셀이 "아직 안 함"인지 "누가 했는데 안 적었음"인지 구분되지 않는다.

만들려는 것은 ERP UI가 아니라 **주문 행의 상태 + 담당자 + 시각**을 권위 있게 보유하고,
교대 경계를 넘어 살아남는 공유 운영 상태 계층이다.

**설계 리트머스**: *디스코드 스크롤백 없이, 처음 보는 야간 담당자가 화면만 보고 지금 뭘
해야 하는지 정확히 아는가?* 모든 결정을 이 문장에 대본다.

## Demand Evidence

- 현재 시스템: 구글 공유 스프레드시트 + 디스코드 (원문: "현재는 직원들끼리 구글 공유
  스프레드시트와 디스코드로 **소통**하고 있어")
- 사용자 규모: 5명 이상, 교대·야간 포함
- 명시적 요청 3건: ① 주문 취합→출고 ② 재고 수량 맞추기 ③ 거래처 저장
- 통증 유형: 반복 수작업으로 시간 소모

**증거 강도 (솔직히)**: 중간. 관찰된 행동(시트+디스코드 운용, 교대 편성)은 실재하지만
"몇 시간을 쓰는가", "지난달에 이것 때문에 무슨 사고가 났는가"라는 숫자가 없다.
그 숫자를 얻는 것이 The Assignment다.

## Status Quo

| 요소 | 현재 도구 | v1에서 | 근거 |
|---|---|---|---|
| 데이터 저장 | 구글 시트 | 대체 | |
| 동시 편집 | 구글 시트 | **약화 수용** (낙관적 잠금) | 5명 교대에서 동시 접속은 보통 1~2명 |
| 대량 붙여넣기 | 구글 시트 | **의도적 포기** | P1' — 붙여넣기를 빠르게 하는 대신 import로 없앤다 |
| 임의 컬럼 추가 | 구글 시트 | **의도적 포기** | P1' — 손대는 필드를 4개로 줄이는 것이 목표 |
| 상태 필드 | 디스코드 대화 | 대체 (핵심) | |
| 감사 로그 | 디스코드 + 시트 버전기록 | 대체 (행별 이력) | |
| 교대 인계 | 디스코드 메시지 | 대체 (핵심) | |
| 알림 | 디스코드 | **유지** — 도구가 디스코드로 쓴다 | 팀이 이미 보고 있는 곳 |

**핵심**: 디스코드를 없애려 하면 안 된다. 도구가 디스코드에 webhook으로 **쓴다**.

## Premises (사용자 합의 완료)

| | 전제 |
|---|---|
| **P1'** | 병목은 입력 속도가 아니라 **입력 자체**다. 주문 취합은 채널 엑셀 import + 중복제거 문제이고, 직원이 손대는 필드는 4개(상태·담당·메모·송장)로 줄어야 한다. v1에서 스프레드시트 클론 그리드는 만들지 않는다. |
| **P2'** | 필요한 건 "누가 언제 뭘 했나"(귀속 + 이력)이지 "누가 뭘 할 수 있나"(RBAC)가 아니다. 단, 로그인과 "인증 사용자만 접근" RLS는 개인정보 때문에 1일차다. |
| **P3** | 레이아웃 30종은 **시각 언어와 셸의 자산이지 로직 자산이 아니다.** v1의 화면 로직은 사실상 전부 신규다 (Feasibility 참조). |
| **P4'** | v1은 주문 취합 하나만 끝까지. 재고(#2)는 v1 관찰 후 결정. |
| **P5** | 주문 데이터는 개인정보다. RLS·이력 컬럼 화이트리스트·마스킹을 **첫 import 전에** 정한다. |

**폐기된 전제 (세션 중 교차검증으로 반박됨)**
- ~~구글 시트만큼 빠른 대량 편집 그리드를 만들어야 한다~~ → 구글의 홈그라운드에서 2~3주짜리
  싸움을 하면서 새 가치를 0 추가한다. 타이핑을 빠르게 하는 게 아니라 없앤다.
- ~~5명 교대면 RBAC이 1일차다~~ → 하나의 무제한 시트를 공유하는 팀에 권한 매트릭스는 퇴행이다.

## Landscape (3-layer)

- **L1**: 스프레드시트는 확장 안 되고, 사본이 갈라지고, 동시 처리에서 오류가 는다.
- **L2**: 사방넷·셀메이트 등 통합관리솔루션을 사서 발주·재고·정산을 묶어라.
- **L3 (EUREKA)**: 업계 글은 스프레드시트의 **단점**만 나열한다. 대체 실패의 원인은 대체품이
  스프레드시트의 **장점**(붙여넣기·키보드 속도·동시 편집)을 못 따라가서다. ERP 도입 실패를
  "직원 저항"이라 부르지만 실제로는 **입력 속도 퇴행**이다.
  → 함의: 이 팀의 정답은 "더 빠른 입력"이 아니라 "입력 제거(import)"다.

## Cross-Model Perspective (Claude 서브에이전트 콜드 리드)

- **Steelman**: "They are not building an ERP or a UI kit. They are building the shared
  operational state layer... one authoritative row per order carrying a status, an owner, and
  a timestamp, deduped across sales channels, that survives a shift change without anyone
  reading Discord scrollback."
- **가장 드러내는 단서**: 사용자가 쓴 동사가 관리가 아니라 **소통**이다. 없는 건 그리드가
  아니라 행마다의 상태·담당자·시각.
- **반박된 전제**: "The bulk typing exists only because there is no import path. A screen that
  is 3x slower per-cell than Sheets but eliminates 95% of the cells being touched wins."
  - *반증 조건*: 손으로 치는 셀의 80% 이상이 이미 보유한 채널 export에서 전사된 것이면 임의
    셀 편집은 사중이다. 넘지 않으면 그리드를 다시 논의한다. → Assignment 2번
- **블라인드 스팟**: (a) 주문은 import 후에도 변한다(취소·반품·부분출고) — 불변으로 취급하면
  도구가 **취소된 주문을 출고하라고 지시**한다. (b) SKU/옵션명 채널 간 매칭은 자유 텍스트
  매칭이고 담당자가 있어야 하는 지속 작업이다. (c) 약한 RLS의 클라이언트 SPA는 대체하려는
  구글 시트보다 **더 나쁜 보관자**다.

## Approaches Considered

### Approach A: 수직 슬라이스 (Import → 작업 큐 → 송장) — 미채택
주문 취합 하나를 끝에서 끝까지. Effort M, Risk Low-Med. **미채택 사유**: 사용자가 B를 선택.

### Approach C: 시트 옆에 붙이기 (정찰) — 미채택
Sheets API로 읽어 상태만 별도 관리 + 디스코드 봇. Effort S. **미채택 사유**: 사용자가
만들겠다고 한 ERP에 도달하지 못한다.

### Approach B: 상태 계층 먼저 — **채택**

## Recommended Approach

**채택: Approach B.** 사용자 선택이며, 진행자 추천은 A였다. 불일치를 기록해 둔다.

**A와 B의 실제 차이 (리뷰어 지적 반영).** B의 완화책("import를 1주차에 붙인다")을 적용하면
화면 순서는 A와 같아진다. 남는 차이는 **불변식이 어디 사는가** 하나다.

> **B = A의 화면 순서 + 상태·귀속·이력을 앱 코드가 아니라 DB(트리거·제약·RLS)에 둔다.**

이 차이는 실질적이다. 이력이 앱 코드에 있으면 벌크 업데이트나 SQL 직접 수정에서 구멍이 나고,
나중에 재고가 붙을 때 같은 코드를 두 번 쓴다. 트리거에 있으면 어떤 경로로 바뀌어도 남는다.

B의 리스크와 완화:
- *데이터가 안 들어와 관찰이 늦어진다* → import를 인프라의 일부로 취급, 1채널 xlsx를 1주차에.
- *도메인 확정 전 상태 전이 고정 → 마이그레이션* → 상태 목록을 코드가 아니라 **관찰에서**
  가져온다(Assignment 1번). v1은 상태 값·표시명 모두 앱 상수 맵으로 두고, 전이 규칙 테이블화는
  상태 목록이 실사용으로 확정된 뒤(v2).

### 스택 (확정)

| 층 | 선택 | 비고 |
|---|---|---|
| 프론트 | 기존 Vite + React 19 + shadcn/ui 유지 | 이미 있음 |
| 백엔드 | **Supabase** (Postgres + Auth + RLS) | 인증·감사를 직접 만들면 수 주 |
| 이력 | Postgres 트리거 3개 (BEFORE×2 + AFTER×1 — 데이터 모델 절의 표 참조) | **화이트리스트 컬럼만** (P5) |
| 엑셀 파싱 | **SheetJS (xlsx)** | ⚠️ 커뮤니티 빌드는 npm이 아니라 `cdn.sheetjs.com` 배포. 사내 프록시 환경이면 블로커 → Dependencies |
| 검증 | **zod** | 행별 판정 사유 표시에 필요 |
| 표 | 기존 shadcn `Table` 프리미티브 + 자체 선택 상태 | TanStack Table이 벌어줄 것은 **행 선택 모델과 페이지네이션 모델**인데, 선택은 `Set<id>` 하나면 되고 페이지네이션은 Supabase `range()` 서버 페이징이라 클라이언트 모델이 필요 없다. 정렬·컬럼 리사이즈·가상화는 애초에 요구사항이 아니다 |
| 테스트 | **vitest** | 현재 0. 성공기준 4는 회귀 테스트 없이 보장 불가 |
| 알림 | 디스코드 Webhook — **Supabase Edge Function 경유** | ⚠️ 클라이언트에서 직접 호출하면 webhook URL이 번들에 박혀 누구나 팀 채널에 글을 쓸 수 있다. URL은 Edge Function 환경변수에만 둔다 |

**의도적으로 뺀 것 (YAGNI)**: Supabase Realtime(→ 30초 폴링 + 포커스 리페치, 동시 접속
1~2명), TanStack Virtual(일 수백 건), 전이 규칙 테이블(상태 목록 확정 전), 전역 감사 로그
화면(행별 팝오버로 충분).

### 데이터 모델

```sql
-- 사용자
profiles(id uuid pk references auth.users, display_name text, discord_handle text)

-- 주문 헤더: 상태 머신이 사는 곳
orders(
  id uuid pk,
  channel text not null,
  channel_order_id text not null,
  channel_status text,          -- 채널 원본 상태. 취소 감지의 유일한 근거
  canceled_at timestamptz null,
  ordered_at timestamptz,
  buyer_name text, buyer_phone text, ship_address text,   -- 개인정보
  status text not null,         -- 운영 상태. 값은 앱 상수, 표시명은 앱 상수 맵(DB 컬럼 아님)
  assignee uuid null references profiles,
  waybill_no text null,
  memo text null,
  version int not null default 1,   -- 낙관적 잠금. 트리거가 증가시킨다
  raw jsonb,                    -- 원본 행 보존(매핑 실수 복구용). ⚠️ 개인정보 키는 제거 후 저장 (P5)
  updated_at timestamptz, updated_by uuid references profiles
)
unique index on (channel, channel_order_id)

-- 라인 아이템: 1주문 N SKU. 헤더와 분리하지 않으면 첫 import에서 unique violation
order_items(
  id uuid pk, order_id uuid references orders on delete cascade,
  line_no int,                  -- export 값이 아니라 "파일 내 해당 주문의 행 순번"
  sku_raw text, option_raw text, qty int, amount numeric
)
unique index on (order_id, line_no)
-- 재import 전략: 해당 주문의 order_items 전삭제 후 재삽입 (upsert 아님).
--   채널 export에 안정적 line 식별자가 있다고 가정하지 않는다.
-- ⚠️ v2 예고: 부분출고(아이템 단위 상태)는 안정적 item key를 요구한다. 전삭제·재삽입은
--   아이템 단위 운영 상태를 매 import마다 지운다. 부분출고를 채택하는 순간 이 전략을
--   다시 열어야 한다 — v1에서 바꿀 일은 아니지만 v2에서 발견해서는 안 된다.

-- 이력: 트리거가 씀. 화이트리스트 컬럼만
order_history(
  id bigserial pk, order_id uuid, changed_at timestamptz, changed_by uuid,
  field text, old_value text, new_value text,
  batch_id uuid,                -- 벌크 변경을 한 덩어리로 묶어 보여주기 위함
  source text                   -- 'import' | 'manual' | 'webhook'
)
-- 기록 대상 화이트리스트: status, assignee, waybill_no  (+ memo 는 P5 결정 대기)
-- buyer_* / ship_address 는 절대 기록하지 않는다 (P5)

channel_column_map(
  channel text pk,
  mapping jsonb,                -- 컬럼 매핑
  cancel_status_values text[],  -- 이 채널에서 "취소"로 간주할 channel_status 문자열 집합
  updated_at timestamptz
)

-- import 배치. "직전 배치" = 해당 채널의 가장 최근 import_batch
import_batch(
  id uuid pk, channel text, file_name text,
  imported_at timestamptz, imported_by uuid references profiles,
  counts jsonb,                 -- {신규:N, 갱신:M, 취소전환:K, 스킵:S, 오류:E}
  missing_order_ids uuid[]      -- 직전 배치엔 있었으나 이번에 없는 주문 (취소 처리 안 함)
)
-- order_history.batch_id 는 import 시 import_batch.id, 수동 벌크 시 클라이언트 생성 uuid
```

`orders`에 `needs_review bool not null default false` 추가 — `missing_order_ids`에 오른 행에
세팅한다. 작업 큐/인계 뷰의 `확인필요` 배지가 이 컬럼을 읽는다.

**`orders` 트리거 3개 (실행 순서 명시)**

| 순서 | 타이밍 | 목적 | 비고 |
|---|---|---|---|
| 1 | **BEFORE UPDATE** | `version = OLD.version + 1`, `updated_at`, `updated_by` | AFTER 트리거는 `NEW`를 수정할 수 없다. 반드시 BEFORE |
| 2 | **BEFORE UPDATE** | 컬럼 화이트리스트 강제 (OQ8) — 허용 외 컬럼 변경 시 예외 | RLS는 행 단위라 컬럼 제한은 트리거로 |
| 3 | **AFTER UPDATE** | 화이트리스트 컬럼 diff → `order_history` 삽입 | |

클라이언트는 `UPDATE … RETURNING version`으로 새 `version`을 되받는다. 벌크 부분 성공에서
배치 N에 성공한 행은 `version+1`을 갖고 배치 N+1로 가야 하므로, 되받지 않으면 재시도가
전부 stale로 실패한다.

**v1 마이그레이션 미포함** (v1.1에서 추가):
```sql
partners(id uuid pk, code text unique, name text, contact text, memo text, active bool)
```

**재import UPSERT 컬럼 소유권** (리뷰어 지적: 이게 없으면 구현 착수 불가)

| 소유 | 컬럼 | 재import 시 |
|---|---|---|
| 채널 소유 | `channel_status, ordered_at, buyer_*, ship_address, raw`, `order_items` 전체 | **덮어씀** |
| 운영 소유 | `status, assignee, memo, waybill_no` | **보존** (덮어쓰지 않음) |
| 파생 | `canceled_at` | 아래 규칙으로 **세팅**, 한 번 세팅되면 되돌리지 않음 |

**취소 감지 규칙** (성공기준 4와 그 회귀 테스트가 이 두 줄에 걸려 있다)
1. `channel_status`가 `channel_column_map.cancel_status_values`에 포함되면 `canceled_at = now()`.
   채널마다 문자열이 다르므로(취소/취소완료/CANCEL/반품접수…) 하드코딩하지 않고 매핑에 둔다.
2. **직전 배치에 있었으나 이번 배치에 없는 행**: 자동 취소 처리하지 **않는다**(export 기간
   필터 때문일 수 있음). 대신 `import_batch`에 "이번에 안 보인 행 N건" 목록을 남기고 작업 큐에
   `확인필요` 배지만 띄운다. v1은 여기까지.

`canceled_at IS NOT NULL`인 행은 작업 큐에서 **취소 경고 배지 + 출고/송장 액션 비활성화**.

**낙관적 잠금과 벌크 처리**
- `version`은 트리거가 증가. UPDATE는 `where id = ? and version = ?` 조건부.
- 단건 충돌: "다른 사람이 방금 바꿨습니다" 배너 + 최신값 diff 표시 + 재시도.
- **벌크(20행 일괄 상태변경 중 3행 stale)**: 전체 롤백하지 않는다. **부분 성공 + 실패한 행
  목록 반환 + 그 행만 재시도** 버튼. v1의 핵심 기능이 벌크이므로 전체 롤백은 쓸 수 없다.

**디스코드 webhook 이벤트** (Edge Function이 발신, batch당 1메시지)
| 이벤트 | 본문 |
|---|---|
| import 커밋 완료 | `[import] {채널} 신규 N · 갱신 M · 취소전환 K · 오류 E건 — {사용자}` |
| 벌크 상태변경 | `[상태] N건 → {상태} — {사용자}` |
| 취소전환 발생 | `[주의] 취소된 주문 N건이 감지됨. 출고 전 확인 필요` |

실패 시 재시도하지 않는다(알림은 best-effort). 실패는 Edge Function 로그에만 남긴다.

리뷰어가 파일을 열어 확인한 결과, 최초 문서의 "재사용" 표기는 과장이었다. 정정한다.

| 화면 | 기반 레이아웃 | 실제로 재사용되는 것 | 신규로 써야 하는 것 |
|---|---|---|---|
| Import 3단계 | `form-wizard(16)` | 스텝퍼 UI, 카드 셸 | 파일 드롭, 컬럼 매핑 UI, zod 검증, 행별 판정 표, UPSERT 커밋 |
| 작업 큐 | **`approval-inbox(24)`** | 좌 목록 + 우 상세 + 액션 버튼 셸 | 선택 UI **전무**(24는 `<button>` 리스트에 체크박스·페이지네이션이 아예 없다) → 다중선택·벌크 상태/담당·4필드 인라인 편집·실제 페이지네이션 전부 신규 |
| 행별 이력 팝오버 | `record-timeline(10)` | 타임라인 `<ol>` 약 28줄만 발췌 | Popover 래핑, `order_history` 바인딩, batch 묶기 |
| 교대 인계 뷰 | `dashboard-ops(20)` | **우측 대기열 `<aside>`만.** 좌측 Progress 게이지·`ComparisonChart`는 폐기 | 아래 3블록 명세 전부 |
| 상태 진행 표시 | `workflow-status(25)` | 스텝퍼 마크업 | 상태 상수 바인딩 |

**핵심 정정**: 재사용은 **셸과 시각 언어 수준**이고 로직은 전부 신규다. 최초 문서가 이 표로
3주를 정당화한 것이 가장 큰 오류였다. (참고: `src/components/erp/record-table.tsx`의
`RecordTable`은 `data`/`columns`/`onRowClick` props를 받지만 체크박스가 비제어이고
`TableFooterBar`의 페이지네이션은 `href="#"` 리터럴이다. 작업 큐에서는 이 컴포넌트를 쓰지 않고
새로 만든다.)

**`RecordTable` "교체"의 범위** — 작업 큐에서 쓰지 않는다는 뜻이지 리포지토리에서 제거한다는
뜻이 아니다. `RecordTable`을 import하는 레이아웃이 13개이고 갤러리는 `/gallery`로 계속
살려 두므로 **기존 컴포넌트는 그대로 둔다.**

**Import 행별 판정 클래스** — **순서대로 평가하는 결정 리스트**다. 위에서 먼저 맞는 것 하나로
확정하고 멈춘다. 판정들이 서로 배타적이지 않으므로 우선순위가 없으면 멱등성이 깨진다.

| # | 판정 | 조건 | 배지 | 커밋 포함 |
|---|---|---|---|---|
| 1 | `오류` | zod 실패. **행별 사유 표시** | destructive | X (해당 행만 제외, 전체 롤백 아님) |
| 2 | `취소전환` | 존재 **AND `canceled_at IS NULL`** AND `channel_status` ∈ `cancel_status_values` | destructive | O (`canceled_at` 세팅) |
| 3 | `스킵` | 존재 AND 채널 소유 컬럼 전부 무변경 | outline | X |
| 4 | `신규` | unique key 미존재 | default | O |
| 5 | `갱신` | 존재 AND 채널 소유 컬럼에 변경 있음 (운영 컬럼 보존) | secondary | O |

`취소전환`은 **집합 소속이 아니라 상태 전이**다 (`canceled_at IS NULL`에서만 발화).
이 조건이 없으면 이미 취소된 행이 재import마다 `취소전환`으로 재발화하고 `canceled_at = now()`가
갱신되어, 아래 멱등성 규칙이 깨진다.

**멱등성**: 같은 파일을 두 번 커밋하면 두 번째는 **전부 `스킵`**이 나와야 정상이다.
회귀 테스트로 고정한다.

**교대 인계 뷰 3블록** (리트머스 화면. "야간 담당자가 화면만 보고 뭘 해야 하는지 안다")

1. **내 앞 교대가 처리한 것** — `order_history`에서 `changed_at`이 직전 교대 구간에 속하는
   변경을 `batch_id`로 묶어 표시. "22:00~06:00 김OO: 출고대기 → 송장등록 34건"
2. **지금 대기 중** — `status`별 카운트 + 목록. **`where canceled_at IS NULL and not needs_review`**.
   ⚠️ 이 필터가 없으면 취소된 주문이 "대기 중 34건"에 섞여 카운트된다. 재import는 `status`를
   보존하므로 취소된 행도 `status='출고대기'`를 그대로 갖고 있다. 리트머스 화면에서
   성공기준 4를 위반하는 지점이 정확히 여기다. 클릭하면 작업 큐로 필터링되어 이동.
3. **막힌 것** — `canceled_at IS NOT NULL` OR `needs_review` OR 송장 미등록 N일 초과.
   취소된 행은 **오직 이 블록에만** 나타난다. 이 블록이 비어 있는 것이 정상 상태다.

교대 경계는 **고정 시각 상수**(예: 06:00 / 14:00 / 22:00)로 시작한다. shift 테이블은 v2.
실제 근무표가 불규칙하면 Assignment에서 드러난다.

**기각한 레이아웃과 사유**
- `kanban-board(26)` — 상태 열 드래그는 매력적이지만 교대 인계에는 "내가 뭘 해야 하나"
  리스트가 낫다. 상태 종류가 확정되면 v2에서 재검토.
- `list-tabbed(4)` / `list-basic(1)` — `approval-inbox(24)`가 좌목록+우상세로 더 가깝다.
- `list-advanced-search(3)` (전역 감사 로그) — YAGNI. 행별 팝오버로 충분.
- `widget-board(23)`, `hierarchy-org(29)`, `report-pivot(21)`, `analytics-filters(22)`,
  `document-view(12)` — 데이터가 쌓이기 전엔 빈 화면. 삭제하지 말고 카탈로그로 남긴다.

## Open Questions

1. **상태 목록.** 신규/확인/출고대기/송장등록/완료/보류는 추측이다. → Assignment 1번.
   v1은 값·표시명 모두 **앱 상수 맵**으로 둔다(DB 컬럼 아님). 관찰 결과가 표시명만 바꾸면 마이그레이션이 필요 없고, 값 자체가 바뀌면 1회 UPDATE로 끝난다.
2. **취소·반품·부분출고 모델링.** v1은 헤더 단위 `canceled_at`까지. 부분출고(아이템 단위
   상태)는 v2. 반품은 아직 모델 없음.
3. **채널 수와 각 export 포맷.** 컬럼 매핑 화면의 복잡도가 여기서 결정된다.
4. **export 불가능한 주문(전화·DM·카톡)의 비중.** 유의미하면 폐기한 원안 P1이 되살아난다.
5. **개인정보 정책 — 임계경로 위의 블로커.** 결정 항목: (a) 마스킹 대상 필드 (b) 접속기록
   보관 기간 (c) Supabase 리전 (d) **`memo`를 `order_history` 화이트리스트에 넣을 것인가**
   — 실사용 메모는 "고객이 전화로 주소 변경 010-…" 형태가 되어 P5를 우회할 수 있다
   (e) `raw jsonb`에서 제거할 개인정보 키 목록.
   서울 리전 불가/미선택 시 **국외이전 고지·동의가 배포 블로커**다.
   → **담당: 프로젝트 오너 1인 지정. 기한: Assignment 관찰 종료일 + 3일.** 첫 import가
   v1 1주차이므로 이 날짜를 넘기면 착수가 밀린다.
6. **교대 경계.** v1은 고정 시각 상수로 결정(화면 절 참조). 실제 근무표가 불규칙하면 Assignment에서 드러난다. shift 테이블은 v2. 인계 뷰의
   유일한 미정 지점이고, 리트머스 문장을 만족시키는 화면이라 가장 중요하다.
7. **상태 전이 UI 메타데이터.** 버튼 문구, 필수 입력(송장번호 없이 "송장등록" 불가),
   종료 상태 여부. v1은 앱 상수에 함께 둔다.
8. **컬럼 단위 쓰기 제한.** RLS는 행 단위다. 4개 컬럼만 UPDATE 허용하려면 트리거 또는
   뷰 + `security definer` 함수. v1은 트리거로 간다.

## Success Criteria

1. **교대 인계에서 디스코드 스크롤백을 읽지 않는다.** (측정: 인계 시점 디스코드 메시지 수,
   도입 전후 1주씩)
2. **주문 마감 시간이 줄어든다.** 늘어나면 즉시 실패. (측정: 도입 전 1주 / 후 1주)
3. **주문 시트에 대한 이중 입력이 없다.** **v1 배포 후** 4주 안에 **주문 시트**가 read-only가 되거나 폐기. (시계는 배포일에 시작한다 — v1 자체가 4~6주이므로 착수일 기준이 아니다)
   (재고 시트는 v2 범위이므로 계속 살아 있다 — 시트 전체 폐기는 v1 기준이 아니다)
4. **취소된 주문이 출고 지시로 뜨지 않는다.** 한 번이라도 나면 신뢰가 죽는다.
   회귀 테스트로 고정한다 (vitest, UPSERT 규칙).

## The Assignment

**코드를 쓰기 전에, 야간 교대 한 번을 옆에서 관찰한다. 도와주지 말고 본다.**

네 가지를 적어 온다.

1. **교대 인계 순간 디스코드에 오간 말을 원문 그대로 받아적는다.** 요약 금지.
   → 이 전사본이 상태 머신의 **상태 목록**이다. 사람이 실제로 쓰는 단어가 상태 이름이 된다.
2. **컬럼별로 키 입력을 센다.** 손으로 치는 셀 중 몇 %가 이미 갖고 있는 채널 export에서
   전사된 것인가. 80%를 넘으면 P1' 확정. 넘지 않으면 그리드를 다시 논의한다.
3. **그날 예외를 센다.** 취소·반품·부분출고·주소 변경 각각 몇 건, 지금 어떻게 처리하는지
   한 줄씩. → Open Question 2의 답.
4. **베이스라인 1주치를 기록한다.** 매일 주문 마감 시각, 인계 시점 디스코드 메시지 수.
   → 성공기준 1·2는 이 숫자 없이는 측정 자체가 불가능하다.

그리고 **채널 export 파일 샘플을 받아 둔다** — 주문 1건에 SKU가 2개일 때 행이 어떻게 나오는지
확인하는 것이 데이터 모델의 1일차 블로커다.

관찰 없이 B를 4주 만들면, 잘못된 상태 머신을 정성껏 만들게 된다.

## Reviewer Concerns (미해결 — 사람이 정해야 함)

적대적 리뷰 3회를 돌렸고(6 → 8 → 8), 명세 이슈는 대부분 닫았다. 남은 둘은 문서 안에서 답을
만들 수 없다.

1. **`raw jsonb`의 목적과 개인정보 정책이 서로를 무효화한다.** 이 컬럼의 명분은 "매핑 실수
   복구용"인데, 복구할 가치가 가장 큰 필드가 정확히 `buyer_name/buyer_phone/ship_address`다.
   개인정보 키를 제거하면 컬럼이 제 목적을 못 하고, 남기면 P5가 무너진다.
   → **택일 필요**: (a) 복구 명분을 버리고 비-개인정보 진단용 blob으로 격하 (b) 개인정보를
   유지하되 `orders` 밖 단기 보관 암호화 저장소로 옮기고 TTL을 명시.
   OQ5(e)는 이 선택을 미뤄 놓았을 뿐 해소하지 않았다.

2. **P5의 담당자가 아직 사람 이름이 아니다.** "프로젝트 오너 1인 지정"은 지정하라는 지시이지
   지정이 아니고, 기한 "Assignment 관찰 종료일 + 3일"은 아직 존재하지 않는 날짜를 기준으로 한다.
   → **필요**: 이름 1개, 그리고 Assignment의 달력상 종료일.
