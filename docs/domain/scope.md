# 도메인 범위와 순서

무엇을 만드는지, 어떤 순서로 만드는지. 이 문서가 도메인에 관한 현행 결정입니다.

이전 초안은 [prior-design-2026-09-02.md](prior-design-2026-09-02.md)에 보관돼 있습니다.
살린 것과 버린 것은 4장에 있습니다.

---

## 1. 무엇을 만드나

**쇼핑몰 운영팀의 주문 취합 시스템.**

5명 이상이 교대·야간 근무로 돌아가는 팀이 구글 공유 스프레드시트와 디스코드로 주문·재고를
관리하고 있습니다. 시트는 데이터를 담고 디스코드는 그 데이터의 **상태**를 담습니다 —
"이거 처리했어요?" "네"가 현재의 워크플로 엔진이자 감사 로그입니다.

교대가 바뀌면 다음 사람은 디스코드 스크롤백을 읽어야 지금 뭘 해야 하는지 압니다.
빈 셀이 "아직 안 함"인지 "누가 했는데 안 적었음"인지 구분되지 않습니다.

만들 것은 ERP 화면이 아니라 **주문 행의 상태 · 담당자 · 시각을 권위 있게 보유하고
교대 경계를 넘어 살아남는 공유 운영 상태 계층**입니다.

### 설계 리트머스

> 디스코드 스크롤백 없이, 처음 보는 야간 담당자가 화면만 보고
> 지금 뭘 해야 하는지 정확히 아는가?

모든 화면 결정을 이 문장에 대봅니다. 통과하지 못하면 그 화면은 아직 덜 된 것입니다.

## 2. 레이아웃 30종의 역할

`frontend/src/layouts/`의 30종은 **제품이 아니라 부품**입니다. 그리고 동시에
**사람과 에이전트 사이의 공용 어휘**입니다.

작업 지시가 이렇게 나갑니다.

```
"상품 관리 만들어줘. 레이아웃 1번으로."
```

그래서 규칙이 하나 생깁니다.

### ⚠️ 레이아웃 번호는 불변입니다

`registry.ts`의 `no`는 한 번 부여하면 **바뀌지 않습니다.**

- 재사용 금지 · 재배치 금지. 오늘 1번이 내일 2번이 되면 과거 지시가 전부 틀어집니다
- 레이아웃을 빼도 **번호는 결번으로 남깁니다**
- 새 레이아웃은 마지막 번호 다음(31번)부터 붙입니다
- 이름은 바꿔도 되지만, 번호가 가리키는 **화면 구조**는 바꾸지 않습니다

`/gallery`는 개발용 참고물이 아니라 지시할 때 계속 보는 화면입니다.

## 3. 도메인 순서

아래에서 위로 쌓습니다. 각 도메인은 앞 도메인이 있어야 성립합니다.

| # | 도메인 | 왜 이 자리인가 |
|---|---|---|
| 1 | **사용자 · 권한** | 감사 컬럼(`created_by` · `updated_by`)이 참조합니다. 모든 테이블의 선행 |
| 2 | **상품** | SKU · 옵션. 입고와 주문 라인이 참조할 대상 |
| 3 | **거래처** | 공급처(매입처). 입고가 "어디서 받았는지"로 참조합니다 |
| 4 | **입고** | 상품 × 거래처. 수량이 여기서 처음 움직입니다 |
| 5 | **판매채널** | 스마트스토어 · 쿠팡 등. 채널별 엑셀 컬럼 매핑이 붙습니다 |
| 6 | **주문** | 취합 · 상태 · 담당 · 이력. **원래 목적** |
| 7 | 출고 · 송장 | 주문 다음 |
| 8 | 재고 | 현재고 조회 · 실사 · 조정 |
| 9 | 기부 · 폐기 | 기한 임박·만료 재고를 밖으로. 세무 증빙 |

3번(거래처)이 4번 앞인 이유는 입고 전표가 공급처 없이 성립하지 않기 때문입니다.

> **닫힘.** 상품에 "기본 공급처"를 두지 않기로 했으므로 거래처는 3번 자리를 유지합니다.
> 근거는 [2-product.md](2-product.md) 1.1.

5번(판매채널)이 6번 앞인 이유는 `channel_column_map`이 주문 import의 전제이기
때문입니다. 상품만 있고 채널 매핑이 없으면 엑셀을 읽을 수 없습니다.

### 거래처와 판매채널의 경계

둘 다 "우리 밖의 상대"지만 성격이 다릅니다.

| | 무엇 | 예 |
|---|---|---|
| 거래처 | 물건을 **사오는** 상대 (매입처) | 도매상, 제조사 |
| 판매채널 | 물건을 **파는 경로** | 스마트스토어, 쿠팡 |

지금은 분리합니다. 나중에 B2B로 회사에 직접 판매하게 되면 그 회사는 "매출처"가 되어
거래처 쪽으로 들어옵니다. 그때 거래처에 구분(매입/매출/양쪽)이 생깁니다 — 3번 설계 때
이 구분을 미리 넣을지 정합니다.

### 입고와 재고의 경계 — 닫힘

> **확정.** 수량을 건드리는 모든 도메인이 같은 문 하나(`stock_ledger`)를 지납니다.
>
> - **4번 입고** — 원장과 현재고 테이블의 주인. 수량을 늘리는 행을 쓴다
> - **8번 재고** — 그 숫자를 보는 화면 + 실사 + 조정. 조정도 같은 원장에 행으로 쓴다
>
> 같은 수량을 두 곳에서 관리하지 않습니다. 근거는
> [4-receiving.md](4-receiving.md) 2장.

### 감수한 것

**주문 취합이 늦어집니다.** 팀이 실제로 아픈 곳은 5번인데 거기 닿기까지 도메인 네 개를
먼저 세웁니다. 그동안 팀은 시트 + 디스코드를 계속 씁니다.

대신 얻는 것은 이전 초안의 맹점 해소입니다. 초안의 `order_items`는 상품을 자유 텍스트로
잡고(`sku_raw` · `option_raw`) 채널 간 SKU 매칭을 v2로 미뤄뒀습니다. 상품 도메인이 먼저
서면 주문 라인이 상품 마스터를 참조할 수 있어 그 문제가 애초에 생기지 않습니다.

## 4. 이전 초안에서 살린 것 · 버린 것

| | 판정 |
|---|---|
| 문제 정의 · 리트머스 문장 | **살림.** 1장이 그대로 |
| 성공기준 4개 | **살림.** 측정 방법 포함 |
| 데이터 모델 골격 (`orders` · `order_history` · `import_batch`) | **살림.** 6번 도메인 설계의 출발점 |
| 재import 컬럼 소유권 · 취소 감지 규칙 · 낙관적 잠금 | **살림.** 밀도가 높아 다시 도출하기 아깝습니다 |
| Postgres · zod · vitest · Discord webhook | **살림.** 3단계에 그대로 |
| "v1은 주문 취합 하나만" 범위 | **버림.** 3장의 순서로 대체 |
| **Supabase** | **버림.** 범위가 도메인 9개로 늘며 트랜잭션 로직이 생겼습니다 → [stack.md](../stack.md) 6장 |
| 트리거 3개로 이력 남기기 | **버림.** 애플리케이션으로 옮김. `changed_by` 와 `source` 를 트리거가 모릅니다 |
| SheetJS 엑셀 파싱 | **버림.** 서버 파싱이므로 Apache POI |
| `order_items.sku_raw` 자유 텍스트 | **확정.** 상품 마스터(`product_variant`) 참조 |
| 감사 컬럼 (`updated_at` · `updated_by`만) | **확정.** 컨벤션의 5종 |
| 상태 값 목록 | **확정.** 접수 · 확인 · 출고대기 · 출고완료 · 보류 + 취소는 별도 축 → [6-order.md](6-order.md) 2장 |

## 5. 진행 상황

진행 방식은 도메인마다 같습니다.

```
용어사전 추가 → 개념 모델 → 화면 (레이아웃 번호 지정) → 구현
```

| # | 도메인 | 상태 |
|---|---|---|
| 1 | 사용자 · 권한 | **설계 완료** — [1-user.md](1-user.md) |
| 2 | 상품 | **설계 완료** — [2-product.md](2-product.md) |
| 3 | 거래처 | **설계 완료** — [3-partner.md](3-partner.md) |
| 4 | 입고 | **설계 완료** — [4-receiving.md](4-receiving.md). 재고 경계 닫힘 |
| 5 | 판매채널 | **설계 완료** — [5-channel.md](5-channel.md) |
| 6 | 주문 | **설계 완료** — [6-order.md](6-order.md). 원래 목적 |
| 7 | 출고 · 송장 | **설계 완료** — [7-shipping.md](7-shipping.md) |
| 8 | 재고 | **설계 완료** — [8-stock.md](8-stock.md) |
| 9 | 기부 · 폐기 | **설계 완료** — [9-disposal.md](9-disposal.md) |

**9개 도메인 설계가 모두 끝났습니다.** 3·4단계(기술 스택 · 스택 종속 컨벤션)도
확정됐고, 남은 것은 [TODO.md](../../TODO.md) 5단계 착수입니다.

> 9번은 설계 도중에 추가됐습니다. 8번의 「기한 임박」이 갈 곳이 없다는 게
> 드러났기 때문입니다. 판매채널에 「기부」 판매처를 넣는 안을 먼저 검토했고
> 채택하지 않았습니다 — 근거는 [9-disposal.md](9-disposal.md) 1장.

용어사전은 [glossary.md](glossary.md)에 누적합니다. 도메인 하나를 설계할 때마다
그 도메인 절을 붙입니다.

## 6. 초안의 미결은 전부 닫혔습니다

이전 초안에는 개인정보 정책 · `raw jsonb` 취급이 미결로 적혀 있었습니다.
**당시에는 여기로 옮겨오지 않았습니다** — 1번 사용자 도메인을 시작하는 시점에
막고 있지 않은 것을 "막힌 것"으로 적으면 실제로 막혔을 때 구분이 안 되기 때문입니다.

해당 도메인 설계에서 꺼내 닫았습니다.

| 미결 | 닫힌 곳 |
|---|---|
| 개인정보 정책 | [3-partner.md](3-partner.md) 3장 · [6-order.md](6-order.md) 7장 |
| `raw jsonb` 와 개인정보 충돌 | [6-order.md](6-order.md) 1장 — 수령인 열을 뺀 채로 저장 |

결정과 기각 근거는 [adr/](../adr/) 에 단계별로 있습니다.
